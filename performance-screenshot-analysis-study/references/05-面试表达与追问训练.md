# 面试表达与追问训练

本篇不是再介绍新功能，而是把前面已经学过的内容变成能直接说出口的答案。回答顺序始终保持：先结论，再流程，再说明代码和模型的职责边界，最后给限制和改进方向。

## 1. 建议的项目介绍结构

### 开场 20 秒

> 我做的是一个 性能采集平台 截图性能联合分析工具。它把性能时序、录制截图和多模态模型组合起来：代码先定位性能异常，模型再识别异常场景并生成有数据边界的解释和复测建议，同时还可以独立检测性能数据正常但画面异常的问题。

### 继续 1 分钟

> 输入可以是本地 性能采集平台 JSON、Excel 和 screenshots 截图，也可以是云端 reportId。程序先统一数据格式，基于目标帧率、FrameTime、FPS、SevereJank、CPU 和温度做本地异常检测；接着把同一画面附近的多条异常合并为事件，只选择有代表性的事件识别截图场景。联合分析分两轮：第一轮模型只决定需要查看的维度，代码再提供真实可用的 GPU、内存或 CPU 细项，第二轮模型生成解释。最后对相似事件聚类，生成经过真实指标校验的复测方案和 HTML 报告。

### 最后 1 分钟强调价值和边界

> 核心设计是让代码负责可重复的检测、数据选择、校验和降级，让模型负责视觉场景、语义归类和辅助解释。模型不会直接决定某个数据点是否异常，也不能越过未采集的数据边界。画面扫描与性能主线分离，因为白屏或 UI 错乱不一定反映在 FPS 上。最终交付是一份带截图、异常证据、分析假设和复测步骤的离线报告，帮助测试人员更快从曲线定位到具体场景。

## 2. 高频追问：从短答到展开

### Q1：为什么不用大模型直接分析 性能采集平台 全量数据？

**短答：** 全量数据和截图太多，成本高、上下文噪声大，且异常阈值应该由可重复的代码规则定义，不应由模型临场决定。

**展开：** 程序先检测明确的慢帧、严重 FPS 下跌、SevereJank、CPU 尖峰和升温趋势，再将同一画面附近信号合并为事件，最多选 25 个代表事件。模型只处理少量事件的场景和解释。这样“异常为什么被发现”可以通过阈值复现，而模型用于它更擅长的语义问题。

**不要说：** “模型直接看曲线比规则更准确。”本项目没有实现全量曲线模型检测，也没有评估这种结论。

### Q2：你怎么判断 FrameTime 异常？

**短答：** 先根据本次 FPS 分布推断目标帧率，得到帧预算；逐帧耗时必须同时满足业务上明显慢和统计上明显离群。

**展开：** 阈值为 `max(2×帧预算, 均值+3×标准差)`。120 FPS 的预算约 8.33ms，60 FPS 约 16.67ms，因此同一个 30ms 帧在不同目标帧率下影响不同。相邻 800ms 内慢帧只保留最高峰，减少一次卡顿产生多条重复记录。

**可讨论改进：** 动态帧率产品可按场景或滑动窗口推断目标 FPS，而不是整段只用一个档位。

### Q3：为什么要把异常点合成事件？

**短答：** 用户体验中的一次卡顿往往在多个指标上同时出现，逐条解释会重复且割裂。

**展开：** 代码先按截图分组，再按 2 秒窗口合并。事件保留内部所有异常，因此联合分析可以同时看到 FrameTime、SevereJank 和 FPS。500ms 去重与 2 秒事件合并是两层不同处理：前者处理瞬时重复信号，后者组织多指标问题。

### Q4：VLM 和 LLM 分别做什么？

**短答：** VLM 看截图，输出场景；LLM 读场景文字和指标，输出解释、聚类和复测方案。

**展开：** VLM 输入目标截图和前后帧，输出应用、场景、操作趋势、UI 和置信度。LLM 不直接看原始图，它先根据核心快照分诊、选择要下钻的数据维度；代码取真实细项后，LLM 生成联合解释。语义聚类和复测方案也由 LLM 完成，但事件覆盖性和指标真实性由代码检查。

### Q5：怎么避免模型编造 GPU 或内存结论？

**短答：** 模型只能从代码提供的可用维度中选择，最终解释只拿到真实采集细项；缺数据必须标注为推测。

**展开：** 第一轮分诊的维度会被代码白名单过滤。第二轮只提供 `get_dimension_metrics` 返回的真实数据。复测方案中的观察指标再和真实指标名单核对。如果本次没有 GPU 利用率，模型不能把“GPU 96%”写进事实，也不能在方案里要求观察该指标。

### Q6：模型输出不稳定时怎么办？

**短答：** 用结构化输出、完整性校验、失败反馈重试和确定性降级，而不是只依赖 prompt。

**展开：** 场景、联合解释、聚类、方案和视觉扫描都有固定工具字段。视觉扫描检查每批是否漏图；聚类检查事件编号是否重不漏；方案检查观测指标是否真实。失败会把具体错误反馈到下一轮；最终失败有不同降级，例如聚类回退简单规则、方案回退固定计划、视觉核查失败保留原结论。

### Q7：视觉扫描为什么要三态和整段核查？

**短答：** 单帧或局部连续帧常有不确定性，直接二分类会把不清晰情况伪装成确定结论；批次之间也可能不一致。

**展开：** `suspect` 专门保留给范围有限、持续短或看不清的画面。扫描结束后，系统用全时段文字摘要检查相似画面是否被判成不同等级、持续时间是否矛盾。重写依据成功后才更新最终结论。它仍不自动断言底层根因，重点是发现需要人工处理的画面状态。

### Q8：并发怎么保证正确性？

**短答：** 视觉批次之间没有依赖，所以并发请求；每批结果按原编号回收排序，token 记录加锁并且每批单独返回统计。

**展开：** `ThreadPoolExecutor` 适合等待 HTTP 请求。完成顺序可能改变，但结果放在以批次号为键的字典，最终排序汇总。全局 token 列表用 Lock，批次统计不从全局列表切片，避免不同线程记录相互混入。

### Q9：云端 MCP 与本地数据如何统一？

**短答：** 云端只负责取元数据、时序和截图；解析后转换成与本地完全相同的 `PerformanceDataBundle`，后续主线不区分来源。

**展开：** MCP 使用 Streamable HTTP JSON-RPC，带 token 和 session。云端表格化时序文本载荷被解析为逐秒采样，截图 Base64 保留内存。后续检测、事件、场景、联合解释和报告复用本地实现。这样数据源变化不会扩散到业务算法。

## 3. 可以主动提出的局限和改进

主动说明限制不减分，关键是明确当前边界和下一步改法。

| 当前限制 | 原因 | 可行改进 |
|---|---|---|
| 异常检测只覆盖明确实现的几类指标 | extra 指标虽能解析，但未定义方向和阈值 | 为每类 extra 定义方向、窗口、阈值和重要度，做可配置检测器 |
| 本地截图只取最近一张 | 当前没有最大关联距离 | 加最大距离、关联置信度和“无可靠截图”状态 |
| 目标 FPS 用整段一个档位 | 适合固定帧率为主的录制 | 按场景或滑动窗口分段推断 |
| 根因主要是辅助判断 | 只有性能快照和截图，没有函数级 trace/日志 | 接入 trace、资源加载、GC、渲染事件和版本对比 |
| VLM 画面结论可能有误 | 图片信息有限、模型存在不确定性 | 保留 suspect、人工审核、积累标注集评估准确率 |
| HTML 大 | 图片内嵌 Base64 | 分离图片资源、生成缩略图、按需加载 |
| HTML 文本安全性不完整 | 某些字段直接字符串拼接 | 统一转义模型和原始数据文本，使用模板渲染 |
| Excel 依赖未写入 requirements | 代码内部 import openpyxl | 补齐依赖和锁版本 |
| 缺少自动化测试 | 项目以脚本开发为主 | 为解析、阈值、表格化时序文本载荷、校验器、缓存、并发建立 fixture 测试 |

## 4. 面试时如何讨论进一步设计

如果被问“还会怎么做”，按优先级回答：

1. **先补可验证性**：为 JSON/XLSX/表格化时序文本载荷 解析、异常阈值、事件聚合、模型输出校验建立单测；用固定样本确保迭代不改变已有结果。
2. **再补数据完整性**：加入截图关联距离、缺失数据标记、Prompt/模型版本和运行参数，保证报告可以追溯。
3. **再扩展检测能力**：把当前 extra 指标从“可展示/可下钻”升级为“可配置检测”，而不是为每个字段手写 if。
4. **最后做诊断闭环**：复测结果回写，比较修复前后的异常数量、FrameTime 分位数和复现率。

这说明改进顺序先保证正确性和可追溯性，再扩展智能能力。

## 5. 最终自测题

不看资料，尝试回答：

1. 这个项目的输入、处理、输出和价值分别是什么？
2. 哪五类性能异常由代码检测？每类为什么规则不同？
3. `PerformanceSignal` 和 `PerformanceEvent` 有什么区别？
4. 场景识别为什么给前后帧？缓存为什么有版本？
5. 两阶段联合分析中，第一轮、代码中间层、第二轮分别做什么？
6. 复测方案怎样避免引用未采集指标？
7. 画面扫描为什么不进性能事件池？它如何并发和核查？
8. 云端数据如何复用本地主线？
9. 模型失败时哪些功能会继续，哪些结果会降级？
10. 你会优先改进哪三个点，为什么？

这十题能完整回答，就已经可以完成项目介绍、深挖追问和设计讨论。
