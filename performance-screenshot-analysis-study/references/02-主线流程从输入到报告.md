# 主线流程：从输入到报告

本篇讲的是整个程序的总流程，不只是一种本地运行方式。后面会用本地 input-set 逐步说明细节，但先用这张总图明确三条路径如何汇合：本地文件和云端 report 的区别只在数据读取；性能主线与画面扫描并列，最后共同进入报告。

```text
本地模式                                      云端模式
JSON/XLSX + .screenshots 截图                      reportId + MCP Token
        │                                             │
        └── 解析原始文件 ───────┐      MCP 拉取元数据、时序、截图 ─┘
                                ▼
                 PerformanceDataBundle：统一的性能数据对象
                                │
          ┌─────────────────────┴─────────────────────┐
          │                                           │
          ▼                                           ▼
性能主线（默认执行）                            画面扫描（指定 --visual-range 才执行）
目标FPS推断 → 异常检测 → 事件合并              选定范围内的全部截图
→ 场景VLM → 两阶段LLM联合分析                  → VLM 三态判读 → 整段一致性核查
→ 问题聚类 → 复测方案                           → visual_findings.json
          │                                           │
          └─────────────────────┬─────────────────────┘
                                ▼
        JSON 结果 + Token 统计 + 内嵌截图 HTML 报告
```

本地和云端最终都被转换为 `PerformanceDataBundle`。它保存设备、应用、逐秒指标、逐帧 FrameTime、截图关联和后续异常；因此性能检测、事件合并、场景识别和联合分析不需要区分数据来源。画面扫描不进入性能事件池，也不参与复测方案；它仅作为报告中并列的质量检查结果追加。

读完本篇，应该能顺着流程完整讲项目，不需要自己把分散功能拼起来。

## 0. 本次运行的输入和最终输出

本地运行输入通常是：

```text
sample_input/
  <录制名>.json 或 <录制名>.xlsx      性能采集平台 导出数据
  <录制名>.screenshots/                   录制期间保存的截图
```

最终输出是：

```text
scene_cache.json   发生代表异常时截图的场景识别缓存
event_analysis.json     每个代表异常事件的完整分析结果
verification_plans.json      相似问题的复测方案
model_usage.json       每次模型调用和各阶段 token 汇总
analysis_report[N].html   内嵌截图、可离线打开的最终报告
```

如果加了 `--visual-range`，还会增加 `visual_findings.json`，并把画面扫描内容追加到 HTML。

## 1. 找到文件并转换为统一性能数据

### 程序做什么

`pipeline.py` 的 `discover_input_set` 在指定目录中寻找 `.screenshots` 截图目录和 JSON/XLSX 数据文件。数据文件优先选择和 screenshots 同名的文件；若没有同名文件，使用候选中的第一个。

之后 `load_performance_bundle` 调用 JSON 或 XLSX 解析器，得到 `PerformanceDataBundle`。这个对象是整条主线共享的内存数据：它保存设备型号、应用名、系统、录制时长、逐秒采样、逐帧 FrameTime 和后续异常列表。

### 为什么先统一数据

JSON、Excel 和云端 MCP 的字段组织不同。如果后面的检测和模型分析直接理解三种格式，代码会出现大量来源分支。项目选择先转换为同一对象，后续所有逻辑只读取 `PerformanceDataBundle`。因此“本地 JSON”“本地 Excel”“云端 report”只有解析阶段不同，检测、场景、联合分析和报告逻辑相同。

### 具体保存什么

一条逐秒采样记录保存：时间、FPS、由 FPS 计算的这一秒平均 FrameTime、Jank、SevereJank、应用 CPU、整机 CPU、温度、网络、截图文件名等。逐帧数据单独保存为“时间毫秒 + 该帧耗时毫秒”，因为它比逐秒平均值更适合定位真正卡住的单帧。

除了已知指标，解析器还会收集原始数据里其它数值型字段，例如 GPU 利用率、内存 PSS、GC 次数、DrawCall。它们会被标记单位和诊断维度，例如 GPU/内存/CPU。全程数值完全不变的额外指标会删除，避免把没有变化的噪声带入后续分析。

### 这一段是硬逻辑还是模型判断

完全是代码硬逻辑。输入相同，得到的统一数据结构相同。

### 实现定位

`pipeline.py: discover_input_set/load_performance_bundle`；`core/telemetry.py: parse_metrics_json/parse_metrics_xlsx/_extract_additional_metrics/_remove_constant_metrics`。

## 2. 根据本次录制推断帧率目标，再找异常

### 程序做什么

程序不会默认所有游戏都跑 60 FPS。它统计整段非零 FPS，先取中位数并映射到 30、45、60、90、120、144 中最接近的档位；再检查该档位周围样本占比是否合理。如果中位数档位的占比明显低于其它档位，改用占比最多的档位。

得到目标 FPS 后，计算每帧预算。例如：

- 60 FPS 的预算约为 16.67ms；
- 120 FPS 的预算约为 8.33ms。

随后代码检测五类问题：

1. **FrameTime 慢帧**：逐帧耗时至少达到“2 倍帧预算”和“均值加 3 倍标准差”两者中较大的阈值。
2. **FPS 严重下降**：同时低于目标 FPS 的 60%、整段平均 FPS 的 70%、绝对流畅线。
3. **SevereJank**：性能采集平台 已记录大卡顿次数大于 0。
4. **应用 CPU 尖峰**：高于平均值加 2.5 倍标准差，且高于 40%。
5. **CPU/GPU 持续升温**：采样数至少 30 个，前段与后段平均温度差至少 8℃。

每次命中都会产生一个 `PerformanceSignal`。它不只是一个数字，还保存异常时刻、基线、偏离程度、中文描述和最近截图名。

### 为什么要这样设计

- FrameTime 用本次推断出的帧预算，避免把 120 FPS 游戏按 60 FPS 规则判断。
- FPS 需要三重条件，避免把仍然可接受的波动误报为严重掉帧。
- SevereJank 是 性能采集平台 已定义的严重事件，直接纳入。
- 温度判断看整体趋势，因为温度不是通常意义上的短时尖峰指标。
- 每种指标的异常语义不同，因此不使用一个通用“超过均值 3 倍标准差”的算法处理所有数据。

### 这一段是硬逻辑还是模型判断

完全是硬逻辑。模型还没有被调用。

### 实现定位

`core/telemetry.py: infer_target_frame_rate/detect_performance_signals/_merge_peaks/_detect_rising_trend/_dedup_by_time`。

## 3. 将异常点变成“需要解释的一次事件”

### 程序做什么

一个短卡顿经常同时出现慢帧、SevereJank、FPS 下跌。若把它们分别交给模型，会得到多条重复解释。项目会先按关联截图分组，再将同一截图内相邻不超过 2 秒的异常点合成一个 `PerformanceEvent`。

事件保存所有原始异常点，报告中可以同时看到“FrameTime 峰值、SevereJank、FPS 骤降”。事件严重度取组内最大值。

如果事件数超过 25，`select_representative_events` 会挑代表事件：尽量覆盖不同主要异常类型、不同 60 秒时间段，并优先选择严重度高的事件。这样模型预算被用在有代表性的样本上。

### 为什么这样设计

事件才是测试人员理解问题的单位，而单个指标只是同一问题的信号。Top 25 不是删除检测结果，而是控制模型调用量和报告重复度。

### 这一段是硬逻辑还是模型判断

完全是硬逻辑。

### 实现定位

`core/telemetry.py: group_signals_into_events`；`core/report_renderer.py: select_representative_events`。

## 4. 只为代表事件识别截图场景

### 程序做什么

程序收集代表事件关联的截图名并去重，读取 `scene_cache.json`：

- 有有效缓存：直接使用，避免重复请求视觉模型。
- 没有缓存或缓存版本过旧：读取当前截图前后各一张相邻图，调用 `SceneAnalyzer.analyze_with_context`。

视觉模型输出：应用名、应用类别、平台、场景标签、场景说明、关键 UI、置信度和推理说明。场景标签不限定固定集合，例如可以是“对局中-多人交火”“加载转场”“更新确认弹窗”。

### 为什么前后帧要一起给模型

单张图可能只看到黑屏、半透明过渡或一个未展开的界面。前后图让模型知道当前状态是在进入还是退出、是加载前还是加载后。结论仍以中间目标截图为准，前后图只帮助理解操作趋势。

### 为什么有缓存版本

旧版本可能是只看单张图得到的结果。当前逻辑改成前后帧上下文后，用 `scene_cache_version=2` 标记新结果；旧结果不会被误当成同等质量的缓存。

### 这一段是硬逻辑还是模型判断

- 是否需要调用模型、缓存是否有效、取哪几张图：硬逻辑。
- 应用、场景、UI 和置信度：模型判断。

### 实现定位

`pipeline.py: ensure_scene_results/_neighbor_frames/_is_scene_cache_valid`；`core/scene_analyzer.py: SceneAnalyzer`；`core/prompts.py` 和 `core/schemas.py` 定义提示和字段约束。

## 5. 先分诊，再按需取细项，再生成联合解释

### 程序做什么

对每个事件，程序先取该时刻最近的一秒采样，生成核心指标快照：FPS、每秒平均 FrameTime、异常帧峰值、Jank、SevereJank、CPU、温度、卡顿率以及少量通用额外指标。

随后进行两轮模型调用：

**第一轮：分诊。** 输入是场景、事件内所有异常、核心快照和“此刻实际可提供哪些细分维度”。模型只能给初步方向，并选择要下钻的维度，例如 GPU、内存或 CPU。

**代码校验。** 程序过滤掉模型选择但当前并不存在的维度。比如本次没有采集 GPU 数据，模型即使返回 GPU，也不能获得 GPU 细项。

**第二轮：最终联合分析。** 程序只取模型选择且真实存在的细项，例如 GPU 占用、内存 PSS、GC 次数、CPU 各核频率，再连同场景和核心快照交给模型。模型输出画面状态、指标解释、联合分析文本、是否可能被当前场景接受。

### 为什么不一开始把所有指标都给模型

全量指标会增加上下文长度，也会混入与本事件无关的字段。先分诊再下钻让模型只获得与当前问题有关的数据。更重要的是，模型不能把没有采集的指标当成事实。最终提示要求“有数据就引用数值；没有数据只能说推测并说明缺什么”。

### 一个必须说清的细节

FPS=0 时，代码把它解释为该秒没有渲染帧，例如加载或黑屏，不把 FrameTime 写成误导性数值。事件快照还会用事件里真正触发的 FPS、SevereJank、CPU 值修正最近采样值，避免报告出现“标题写 SevereJank=1，快照却显示 0”的矛盾。

### 这一段是硬逻辑还是模型判断

| 内容 | 类型 |
|---|---|
| 选择最近采样、构造快照、列出可用维度、读取细项、过滤不存在维度 | 硬逻辑 |
| 初步怀疑哪个方向、文字解释、是否可接受 | 模型判断 |
| “GPU/内存一定是根因” | 系统不能自动得出，除非有更完整证据 |

### 联合分析的结论边界：必须这样理解

代码能够保证的是**输入事实和数据边界**：事件中有哪些异常、快照取自哪个真实采样点、哪些维度本次确实存在、下钻结果是否来自白名单维度，以及模型不能通过这条调用拿到未采集的细项。代码还要求模型在获得数值时引用数值，在缺少数据时标记为推测。

代码**不能逐句验证**模型写出的因果关系。例如模型写“交火特效可能造成 GPU 渲染压力”，即使它引用了 96% GPU 占用和 95ms FrameTime，这仍是结合场景和指标形成的候选解释，不是代码已经证明的因果关系。当前实现没有逐句事实核验器，也没有函数级 trace、渲染调用栈、资源加载日志或受控对照实验来自动证明根因。

面试中应准确表述为：**代码保证维度存在、快照真实、下钻受限；模型生成解释和候选根因；性能工程师结合复测、日志和代码继续确认因果。** 不应表述为“LLM 已经定位并证明了根因”。

### 实现定位

`core/telemetry.py: summarize_metrics_at/available_dimensions_at/get_dimension_metrics`；`core/event_analyzer.py: EventAnalyzer.explain/_call_triage/_call_joint_with_retry`。

## 6. 把多个事件整理成可执行复测方案

### 程序做什么

联合分析完成后，系统不为每个事件机械生成一份方案。它先将语义上同类的问题归组：例如“加载时黑屏”和“战斗时黑屏”应分开；同一战斗画面中，GPU 压力和内存 GC 的证据不同也应分开。

模型负责给事件归组、命名和说明理由；代码负责检查每个事件编号是否被分到且只被分到一个组。若模型分组失败，回退到“场景名 + 异常类型”相同的简单分组。

每组按出现次数、最慢 FrameTime 和“需要关注”的事件数计算优先级，最多处理 12 组。对每组生成一份方案：目的、操作步骤、观察指标、预计时长、不同结果的判读方式。

程序会把模型提出的观察指标和本次真实指标列表比对。若模型写了“GPU占用”但本次没有采集 GPU 数据，认为方案不合格并要求模型修正。多次失败后，代码产生一份固定兜底方案，仍保证测试人员有可执行步骤。

### 这一段是硬逻辑还是模型判断

- 聚类编号是否完整、优先级、最大组数、指标真实性、兜底：硬逻辑。
- 哪些事件在语义上同类、方案文字和根因假设：模型判断。

### 实现定位

`core/verification_planner.py: VerificationPlanner.plan/_semantic_cluster_with_retry/_validate_clusters/_validate/_fallback`。

## 7. 将结果写成报告

程序把结构化结果分别写 JSON，并调用 `build_html` 生成 HTML。截图会转成 Base64 data URL 直接放进 HTML，因此文件可离线打开，不依赖原 screenshots 路径。报告按事件展示：时间、截图、场景、所有异常类型、核心快照、下钻细项、联合解释和复测方案。

同时 `token_stats` 记录场景识别、分诊、联合分析、语义归类、复测方案等每次调用的输入/输出 token，用于了解成本。

### 这一段是硬逻辑还是模型判断

完全是硬逻辑；它只展示前面已经生成的结果。

### 实现定位

`core/report_renderer.py: build_html/encode_image/next_html_name`；`core/model_usage.py`。

## 用这条主线回答“项目怎么跑”

可以按下面顺序复述：

> 输入是一份 性能采集平台 JSON 或 Excel 和对应截图。程序先统一成内部性能数据，再基于本次录制推断目标帧率，用本地规则找慢帧、严重掉帧、SevereJank、CPU 尖峰和升温趋势。接着把同一画面附近的多条异常合成一次事件，选择有代表性的事件。只对这些事件关联的截图做 VLM 场景识别。然后 LLM 先根据核心快照分诊，代码再只取真实可用的 GPU、内存或 CPU 细项给第二轮模型做联合解释。事件会按问题模式聚类，生成只引用真实指标的复测方案。最后把 JSON、token 统计和内嵌截图的 HTML 报告写到 input-set 目录。
