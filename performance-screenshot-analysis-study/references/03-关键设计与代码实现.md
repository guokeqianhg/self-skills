# 关键设计与代码实现

本篇在主线基础上回答“为什么这样写、代码实际如何保证它工作”。阅读方式是：先看每节的结论，再看实现定位。不要孤立背函数名；函数名只是对具体设计的定位入口。

## 1. 设计一：目标帧率不能写死

### 要解决的问题

FrameTime 是否异常依赖应用期望帧率。60 FPS 下 20ms 只比预算 16.67ms 多一点；120 FPS 下 20ms 已远超 8.33ms 预算。如果代码固定用 60 FPS，会低估高刷游戏的卡顿；固定用 120 FPS 又会误判 30/60 FPS 产品。

### 代码怎么做

`infer_target_frame_rate` 从每秒 FPS 中取非零值：

1. 排序后取中位数，不用平均数。中位数较少被少数掉帧点影响。
2. 将中位数映射到标准档位 `[30, 45, 60, 90, 120, 144]` 的最近值。
3. 对每个档位统计“在该档位 ±10% 且至少 ±5 FPS 范围内”的样本比例。
4. 如果中位数对应档位的比例至少达到最高比例档位的 80%，采用中位数档；否则采用样本比例最高的档。
5. 没有任何非零 FPS 时，使用 60 FPS 作为回退。

然后：

\[
帧预算(ms) = 1000 / 目标FPS
\]

### 面试应怎样说

> 我不固定使用 16.67ms，而是先根据本次录制的 FPS 分布推断目标档位，再计算帧预算。中位数用于抵抗少量掉帧，档位占比校验用于防止中位数恰好落在少数异常样本附近。它适合大多数固定帧率游戏；如果产品存在长时间动态锁帧，下一步可以改成按时间窗口或按场景分段推断。

### 实现定位

`core/telemetry.py: infer_target_frame_rate`；结果写入 `PerformanceDataBundle.target_fps`、`frame_budget_ms`。

## 2. 设计二：不同指标必须使用不同异常规则

### FrameTime：识别真正慢帧

FrameTime 逐帧数据存在时，代码先计算整体均值和标准差，阈值是：

\[
阈值 = max(2 × 帧预算, FrameTime均值 + 3 × 标准差)
\]

只有超过这个阈值的帧才是候选慢帧。取较大值意味着它同时要求业务上明显慢，以及统计上明显偏离。相邻 800ms 内多个慢帧会合为一个，只保留耗时最大的那帧；否则一次短卡顿会产生很多重复事件。

`severity` 在这个指标中是“当前帧耗 / 帧预算”。例如 120 FPS 的预算 8.33ms，95ms 慢帧的严重度约 11.4。这个值主要用于比较和排序，不是产品验收等级。

### FPS：避免把普通波动当严重问题

FPS 降低必须同时满足：

\[
FPS/目标FPS < 0.6
\]
\[
FPS < 整段FPS均值 × 0.7
\]
\[
FPS < min(45, 目标FPS × 0.5)
\]

三个条件分别保证：相对目标掉得多、相对本局状态掉得多、绝对值已经低到影响流畅性。比如 120 FPS 临时降到 60 FPS，虽然下降明显，但不一定被该规则视为严重卡顿。

### SevereJank：尊重 性能采集平台 自身的严重事件定义

逐秒 `severe_jank > 0` 直接创建异常点。此处不再重新计算阈值，因为数据来源已经给出了“大卡顿”语义。

### App CPU：同时看相对异常和绝对占用

只有 `AppCPU > 均值 + 2.5×标准差` 且 `AppCPU > 40%` 才记录。第一层避免把稳定高 CPU 误称为尖峰；第二层避免在整体低负载中把微小波动当性能问题。

### 温度：识别持续变化，不看短时波动

对 CPU/GPU 温度，至少有 30 个点才分析。代码计算开头 20% 与结尾 20% 的平均温度，累计上升至少 8℃ 才记录。异常时间不是最后一秒，而是首次达到中间温度的时刻，目的是让报告可以关联到升温过程中的画面。

### 面试应怎样说

> 我没有用一个统一 z-score 规则处理所有指标，因为慢帧、帧率下跌、性能采集平台 的 SevereJank、CPU 峰值和温度趋势的含义不同。代码把它们分开检测：慢帧同时看帧预算和统计离群，FPS 使用三重门槛，SevereJank 直接采用工具定义，温度看全程趋势。这样规则和用户体验语义更一致。

### 实现定位

`core/telemetry.py: detect_performance_signals/_merge_peaks/_detect_rising_trend`。

## 3. 设计三：异常点要合成事件，不能直接逐条解释

### 要解决的问题

一帧 95ms 慢帧可能同时导致同一秒 SevereJank 和 FPS 降低。分别做三次 AI 分析，会得到三段重复内容，也会增加调用成本。

### 代码怎么做

每个异常点创建时先寻找时间最近的截图。`group_signals_into_events` 先按截图名分组：同一截图意味着相同的画面上下文；同组中时间相邻不超过 2 秒的异常再合并。没有截图时使用时间窗口作为后备分组方式。

事件中保留完整异常列表。`metrics` 属性只是去重后的指标名称列表；真正的异常数值没有被删除。事件严重度取内部最大值。

在检测结束前还有一次 500ms 去重：同一时间桶内优先保留 FrameTime，其次 SevereJank、FPS、CPU；温度趋势不参与。这个去重目的是控制近似重复信号，事件合并的目的是把不同类型但同一问题的信号放在一起，两者职责不同。

### 面试应怎样说

> 我先做了两层收敛。第一层在 500ms 内处理同类瞬时信号的重复，第二层按截图和 2 秒窗口把多指标信号合成一次事件。报告和模型分析面向事件而不是面向单个数据点，因此能同时解释慢帧、SevereJank、FPS 的关联，也减少重复分析。

### 实现定位

`core/telemetry.py: _dedup_by_time/group_signals_into_events/_create_event`。

## 4. 设计四：场景识别是受约束的 VLM，不是自由文本识图

### 要解决的问题

后续联合分析需要稳定字段：什么应用、什么平台、什么场景、画面正在做什么。如果模型只输出一段自由文本，程序很难缓存、展示和组合。

### 代码怎么做

`SceneAnalyzer` 将图片编码为 data URL，向 通用结构化模型接口发送结构化工具定义 `report_scene_result`。工具字段包括应用名、类别、平台、场景标签、描述、UI、置信度和 reasoning。

程序优先读取标准 `tool_calls` 参数。但不同网关可能把工具调用写在正文中，因此存在三层文本回退：识别 兼容网关回退标记 的工具参数标记、识别 `parameters` 对象、识别普通 JSON；单图场景还可从被截断 JSON 中尽力抢救已出现字段。

读取后 `_normalize` 统一格式：字符串缺失补默认值、置信度转数字并限制 0~1、UI 字段统一为列表。调用失败最多重试，重试时轻微提高 temperature，避免模型连续产生同一个格式错误。

### 缓存为什么安全

`scene_cache.json` 按截图文件名保存结果。缓存只有满足“不是错误、版本等于 2”才可用。版本 2 代表当前识别使用了中心帧前后上下文；旧的单帧结论主动失效，避免不同算法产生的结果混用。

### 面试应怎样说

> 场景识别采用结构化输出，而不是让模型随意写描述。代码负责图片编码、前后帧选择、结果解析、格式归一、缓存和重试；模型负责从画面中判断场景。这样场景结果可以可靠地进入后续事件分析，但我仍把置信度和人工校验保留下来，因为识图结果不是确定事实。

### 实现定位

`core/schemas.py`、`core/prompts.py`、`core/scene_analyzer.py`；主流程缓存逻辑在 `pipeline.py: ensure_scene_results`。

## 5. 设计五：两阶段联合分析控制信息量和模型边界

### 第一阶段：分诊

程序提供：事件内所有异常、截图场景、核心快照、当前可以下钻的维度、设备和 GPU 型号。模型只返回：初步判断和希望继续查看的维度名称。

例如，慢帧很高但 CPU 不高，场景又有大量特效，模型可能选择 GPU；若发现内存相关线索，也可能选内存。

### 中间的代码控制

模型返回的维度会和 `available_dimensions_at` 的真实可用列表求交集。模型写出不存在的维度会被丢弃。`get_dimension_metrics` 只返回该时间点、该维度的实际指标，并带上单位。

### 第二阶段：最终解释

第二轮输入只增加已经选中的真实细项。提示词要求：给了数据的方向必须引用具体数值；没有数据时可以说“推测”，同时说明无法验证的原因。结果包括画面状态、指标解释、联合分析和是否可能可接受。

### 失败时怎么办

第一阶段失败：不做下钻，但仍能用核心快照进入最终分析。第二阶段最终失败：程序生成一个可读降级结果，保留场景描述和异常现象，并明确 AI 分析失败；不会让整个报告中断。

### 模型结论的硬边界

这一设计只保证三件事：

1. **维度真实存在**：模型要求下钻的维度必须出现在当前时刻的可用维度列表中。
2. **快照来自真实数据**：核心指标和细项由代码从 `PerformanceDataBundle` 读取，不由模型编造。
3. **下钻范围受控**：第二轮只获得白名单中的指标，拿不到本次未采集的 GPU、内存或其它字段。

它不保证模型写出的每一句因果推断为真。模型可以根据“GPU占用高、FrameTime 高、画面特效多”生成“可能存在 GPU 渲染压力”的候选解释，但代码不会自动验证“特效导致 GPU 压力”这一因果链。根因仍要结合复测、日志、Trace、埋点或代码分析人工确认。

### 面试应怎样说

> 我把联合分析拆成分诊和最终解释。分诊让模型选择信息需求，代码控制它能拿到什么数据。这样比一次性给全量指标更节省 token，也能避免模型把未采集的 GPU 或内存数据当事实。代码保证的是维度存在、快照真实和下钻受限；模型负责生成解释和候选根因。模型的因果措辞不是自动验真的最终结论，仍需通过复测、日志或代码进一步确认。

### 实现定位

`core/event_analyzer.py: EventAnalyzer.explain/_call_triage/_call_joint_with_retry`；`core/telemetry.py: summarize_metrics_at/available_dimensions_at/get_dimension_metrics`。

## 6. 设计六：复测方案必须引用真实指标

### 要解决的问题

模型可能生成看起来专业但无法执行的方案，例如要求观察“GPU占用”，而当前报告没有采集 GPU 指标。这样的方案会误导测试人员。

### 代码怎么做

程序收集核心指标、各事件快照字段和已经下钻的字段，形成真实指标名单。模型生成方案后，代码将方案的指标名称做归一化：忽略空格、括号、单位符号等，然后做模糊匹配。找不到的指标会形成校验错误文本，反馈给模型要求重写。

复测方案包含：验证目标、可执行步骤、观察指标、预计时长、结果判读。最终失败时 `_fallback` 生成固定方案，使用事件真实指标，确保功能不空白。

### 面试应怎样说

> 复测方案的文字由模型生成，但方案是否合格由代码检查。特别是观察指标必须来自这次实际采集数据。模型输出不通过时，程序把具体问题反馈给它重写；多次失败仍有基于真实异常指标的兜底计划。

### 实现定位

`core/verification_planner.py: collect_available_metrics/find_invalid_metrics/_validate/_fallback`。

## 7. 设计七：报告只负责展示，不负责重新判断

`build_html` 读取前面已经得到的事件解释、复测计划、视觉问题和图片，将图片编码为 data URL 后写入单个 HTML。它不重新检测数据，不重新调用模型。这个边界让“计算/判断”和“展示”分开，报告生成失败时不会影响已经写好的 JSON 结果。

需要承认的限制：部分模型文本和数据字段仍通过字符串拼接进入 HTML，生产环境应统一 HTML 转义；内嵌图片让报告可离线查看，但文件体积会增大。

### 实现定位

`core/report_renderer.py: encode_image/build_html/_build_retest_section/_build_visual_section`。

## 8. 一张硬逻辑与模型判断责任表

| 处理步骤 | 代码硬逻辑 | 模型判断 |
|---|---|---|
| 数据解析 | 字段读取、类型转换、额外数值抽取、恒定值清理 | 无 |
| 异常检测 | 帧率推断、阈值、去重、最近截图关联 | 无 |
| 事件组织 | 截图分组、2 秒窗口、Top 25 选择 | 无 |
| 场景识别 | 选图、前后帧、缓存、重试、字段格式 | 应用、场景、UI、置信度 |
| 联合分析 | 快照、可用维度、下钻数据、白名单、降级 | 初步方向、解释、可接受性 |
| 复测方案 | 分组完整性、优先级、指标真实性、兜底 | 语义归组、假设、步骤、判读文字 |
| 画面扫描 | 选帧、批次、并发、输出完整性、报告 | 画面是否正常/可疑/异常、现象文字 |
