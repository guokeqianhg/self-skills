# 扩展能力与可靠性

主线报告解决“性能异常发生了什么”。本篇补充主线之外但面试常被追问的内容：画面异常如何检测、云端数据如何接入、并发如何保证稳定、失败如何降级，以及两个独立工具做什么。

## 1. 独立画面异常扫描：检查性能曲线看不见的问题

### 它解决什么问题

性能主线只能根据指标触发。例如 FPS、FrameTime、SevereJank 都正常时，主线不会产生异常事件。但玩家仍可能看到白屏、花屏、贴图丢失、模型破面、UI 错乱或过大的遮挡。画面扫描就是为这类问题单独设计的。

它不是“给性能异常再做一次截图识别”。它可独立运行：

```powershell
python pipeline.py --input-set sample_input --visual-range 300-400 --visual-only
```

这意味着 300 到 400 秒每一张可用截图都要判读，即使性能数据完全正常。

### 三态结论和字段

每张图片输出 `VisualFinding`：

| 字段 | 作用 |
|---|---|
| `scene` | 这是什么游戏/应用场景，当前大致在做什么 |
| `description` | 只记录可见画面事实，不在这里判断原因 |
| `persistence` | 该表现在哪些图出现、持续多久、是否消失后复现 |
| `verdict` | normal、suspect、abnormal 三态 |
| `issue_type` | 模型按现象自由命名；正常时是“无” |
| `evidence` | 面向测试人员的最终依据：现象、可见证据、影响、待验证项 |
| `confidence/severity` | 模型对判断的把握和影响程度 |

`normal` 表示当前画面状态可以接受；`suspect` 表示范围有限、时间很短或看不清，需要人工确认；`abnormal` 表示画面状态本身明显不应作为正常游戏画面持续出现。

代码特意要求模型不要用“这是正常特效”作为 normal 的唯一理由。原因是识别出来源不等于画面影响可以接受；模型必须描述画面可见范围、内容是否可辨识和持续性。

### 如何批量处理

`VisualQualityScanner` 将帧按 6 张一批切分，批与批之间重复 1 张。重复图仅作为上下文，不要求重新输出，避免重复计费和重复记录。尾部若只剩 1 张图，会并入前一批。

每一批模型输出必须覆盖本批所有需要判读的图片。代码检查：是否漏图、是否重复、是否缺字段、verdict 是否为三种合法值。失败会重试，最终单批失败只记录失败，不中断其他批。

### 为什么使用并发

各图片批次之间没有数据依赖，HTTP 模型请求主要是在等待网络和服务端，因此使用 `ThreadPoolExecutor` 并发。默认并发数为 3，可由 `SCAN_CONCURRENCY` 调整。

并发不会改变输出顺序：每个任务完成后按批次编号放入字典，汇总时再按编号排序。Token 统计既有全局 Lock，也让每批请求返回自己的 token 记录，避免线程完成顺序导致统计混入。

报告同时显示：用户实际等待的墙钟耗时、所有模型请求耗时之和、并发加速比、每帧平均 token 和失败批次数。

### 为什么还要做“整段核查”

每个批次只能看局部连续图片，可能把相同状态判成不同等级，也可能低估持续时间。批次结束后，程序不再发图片，而是将全段的场景、客观描述、持续性和当前结论发给模型做一次文字一致性核查：

1. **定位阶段**：只找哪些帧需要改结论，输出很短。
2. **重写阶段**：只为命中的帧重新写最终依据，允许并发。
3. **应用阶段**：只有新依据成功生成，才更新 verdict、异常类型和严重度；否则保留原记录。

核查阶段不修改场景和客观描述，因为它没有再次看图。旧 verdict 会写入 `initial_verdict`，并标记 `reviewed=true` 方便调试；最终 HTML 不暴露“初判、复核、改写”等内部过程。

### 代码与模型职责

| 内容 | 代码 | 模型 |
|---|---|---|
| 选择时间范围、读取全部帧、切批、重叠、并发、顺序、校验、写 JSON | 是 | 否 |
| 每张图是什么场景、画面现象、持续性、三态、异常名称、最终依据 | 否 | 是 |
| 是否自动确认底层根因 | 否 | 否，模型只能提出需要验证的方向 |

### 实现定位

`core/visual_quality_scan.py: parse_range/select_frames_local/VisualQualityScanner.scan/_make_batches/_call_with_retry/_validate/cross_review`。

## 2. 云端 MCP：不下载原始报告也能复用整条主线

### 它解决什么问题

本地模式要求已经导出的 JSON/XLSX 和 `.screenshots` 目录。云端模式只需提供一个云端报告 `reportId`，程序直接请求平台 MCP：

```powershell
python pipeline.py --report-id <REPORT_ID>
```

需在环境变量中提供 `PLATFORM_MCP_TOKEN=<REDACTED_TOKEN>`，默认 endpoint 为 `https://mcp.example.invalid/v1`。

### 请求流程

1. `PlatformMcpClient.connect` 发送 JSON-RPC `initialize`，读取并保存服务端 session id。
2. `load_remote_report` 拉取报告元数据和所有可用时序指标。
3. MCP 返回的文本是 表格化时序文本载荷：有 metadata 区和 `timeseries[N]{列名}` 表。解析器将它变成内部 `PerformanceDataBundle`。
4. 代表事件确定后，`fetch_event_screenshots` 对每事件的前后约 5 秒请求截图。
5. MCP content 中一条文本如 `[screenshot @ 151.0s]` 与紧随的 image block 配对；Base64 图片只解码到内存字典，不写原始截图文件。
6. 后续异常、场景、联合分析和 HTML 与本地路径完全相同。

### 云端全量画面扫描为什么要先测截图间隔

MCP 单次最多返回约 5 张截图，而且可能是一个时间窗口内的均匀抽样。如果直接请求很大窗口，拿到的 5 张图之间间隔不代表真实采集频率，会遗漏中间帧。

`probe_interval` 先用很窄的窗口多次探测，取相邻截图的最小时间差作为近似采样间隔 Δ。之后用约 `5×Δ` 宽度切分目标扫描范围，逐窗口取图、按真实时间去重。这不是绝对保证服务端不会变更返回策略，但比一次大范围请求更不容易漏帧。

### 代码与模型职责

云端协议处理、表格化时序文本载荷 解析、重试、session、图片时间配对都是硬逻辑；模型并不直接调用 MCP。

### 实现定位

`core/platform_mcp_client.py`；`core/remote_data_source.py: load_remote_report/fetch_event_screenshots/_pair_screenshots`；`core/visual_quality_scan.py: probe_interval/select_remote_frames`。

## 3. 缓存、重试、降级：系统在不稳定输入下如何继续工作

### 场景缓存

场景识别成本较高，结果按截图文件名写进 `scene_cache.json`。有效缓存必须没有 `error` 且版本为当前 2。缓存版本是算法版本，不是文件格式版本：当前版本表示该场景经过前后帧上下文识别。这样更新识别方法后不会错误复用旧结论。

### 模型输出结构与兼容

关键模型调用使用 通用结构化工具调用，强制要求返回指定字段。标准接口返回 tool call 参数；部分兼容模型会把参数写在正文，代码再尝试 兼容网关回退标记 标记、parameters 对象或普通 JSON。场景识别在 JSON 截断时还会尽力提取已经完整出现的字段。

这是为了提高可用性，不代表任何文本都可信。结构完整只说明“程序能读取”，不说明“模型判断正确”。

### 重试策略

常规模型调用最多三次。第 2 次以后小幅提高温度，上限 0.5，减少连续产生同样格式错误的情况。视觉扫描、语义聚类、复测方案还会把上次校验失败的原因追加到下一次 prompt，例如“缺少哪张图”“引用了哪个不存在指标”。

### 按功能的最终降级

| 功能 | 失败后行为 |
|---|---|
| 单张场景识别 | 该图记录 error，批量继续 |
| 主流程场景识别 | 缓存 error；后续运行可重新尝试 |
| 分诊 | 跳过下钻，仍进行最终联合分析 |
| 最终联合分析 | 填入场景描述和异常现象，并标明 AI 分析失败 |
| 语义聚类 | 回退到“场景标签 + 异常签名”分组 |
| 复测方案 | 使用真实异常指标生成固定兜底方案 |
| 视觉扫描某一批 | 该批失败，其他批继续；报告展示已成功结果 |
| 整段核查 | 失败则保留逐帧原结论 |

### 实现定位

`core/scene_analyzer.py`、`core/event_analyzer.py`、`core/verification_planner.py`、`core/visual_quality_scan.py`；缓存编排在 `pipeline.py`。

## 4. 报告、Token 和全量场景存档

### HTML 报告

`build_html` 将图片转换为 `data:image/...;base64,...` 写入 HTML。这使报告拷贝后仍能离线打开，不依赖原图片目录。报告分别显示：

- 基本设备和应用信息；
- 每个代表异常事件的截图、场景、指标、下钻结果和联合解释；
- 问题模式与复测方案；
- 可选的画面异常详情和全帧缩略图。

代价是图片多时 HTML 文件会很大。生产化可改为外部资源、缩略图或对象存储链接。

### Token 统计

`token_stats.record` 在每次模型调用后保存阶段名、标识、输入 token、输出 token、总 token。它用锁保护多线程追加。主流程最终把按阶段汇总和完整明细写入 `model_usage.json`。

这能回答“成本主要花在哪”：场景识别、分诊、联合分析、语义归类、复测方案、视觉扫描和视觉核查可以分别统计。

### 全量场景存档

`build_scene_archive.py` 会遍历 `.screenshots` 内所有图片，已成功识别的图复用缓存，未识别才调用 VLM；每处理一张就写缓存，程序中断后可续跑。最终生成一份每张图片都带场景标签的 HTML。

它适合人工回放和建立场景库，不适合日常性能分析，因为日常只需识别异常关联截图以控制成本。

## 5. 独立图片转视频工具

`image_video/image_to_video.py` 不参与性能分析。它递归收集图片，统一命名和可选尺寸，然后通过 ffmpeg 生成 MP4。

- 简单模式：指定 FPS 或总时长。
- crossfade 模式：每图先编码成短视频段，再用 `xfade` 连接。
- 默认缩放保持比例并补黑边；`--crop` 改为裁剪填满。
- 程序启动先检查 ffmpeg；临时文件默认 finally 清理，`--keep-temp` 才保留。

面试时把它描述为独立工程工具，不要混进性能分析主线。
