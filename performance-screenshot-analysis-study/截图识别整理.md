# 这个项目本质上做什么

它有两条主线：

1. **性能异常分析**  
   读取 PerfDog 的指标和截图，找出卡顿、掉帧、CPU 高、温度升高等问题，再结合截图说明“什么画面下出了什么性能问题”。

2. **画面异常分析**  
   即使 FPS 正常，也可以单独检查截图中有没有白屏、花屏、贴图丢失、UI 错乱、大面积画面异常等。

它不是传统的“训练分类模型”。  
它是：**Python 负责数据处理和规则判断，LLM/VLM 负责看图、理解场景、生成分析结论。**

---

# 一、主入口：`analyze.py`

日常最核心的脚本是：

```powershell
python analyze.py --dataset dataset7
```

它会自动在 `dataset7` 中找：

- 一个 PerfDog 数据文件：`.json` 或 `.xlsx`
- 一个截图目录：`xxx.capture`

整个执行顺序是：

```text
读取 PerfDog 数据
  ↓
检测异常指标
  ↓
把多个异常指标合并成“事件”
  ↓
找每个事件对应截图
  ↓
让模型识别截图场景
  ↓
让模型结合场景和指标解释问题
  ↓
把类似问题聚类
  ↓
生成复测方案
  ↓
输出 JSON、HTML、Token 统计
```

`analyze.py` 只是总调度，真正功能分散在 `agent/` 下。

# 二、PerfDog 数据怎么读取：`agent/metrics.py`

核心数据结构是 `MetricsBundle`，可以理解为“一份完整的性能报告”。

里面包含：

- 设备型号、应用名、CPU、GPU、系统信息；
- 每秒性能数据；
- 每帧 FrameTime；
- 截图文件名和时间；
- 检测出的异常。

每一秒的数据用 `SecondSample` 表示，例如：

```text
第 120 秒：
FPS = 30
App CPU = 85%
BigJank = 1
GPU 温度 = 45℃
截图 = 120.jpg
```

## 1. JSON 解析

函数：`parse_perfdog_json()`

它从 PerfDog 的 `DataList` 中拿常见字段：

- `AndroidFps.fps` → FPS
- `AndroidFps.Jank` → Jank
- `BigJank.BigJank` → 大卡顿
- `CpuUsage.AppUsage` → App CPU
- `CpuUsage.TotalUsage` → 整机 CPU
- `ScreenShot.FileName` → 截图名
- 温度、网络、Stutter 等

逐帧耗时则从：

```text
DataListNew.FrameDetails
```

读取。

## 2. 额外指标怎么处理

PerfDog 导出的字段不固定，例如有些报告会带：

- GPU 占用；
- 显存；
- Java Heap；
- Native Heap；
- GC 次数；
- CPU 核频率；
- GPU Counter；
- 自定义指标。

代码不会要求这些字段必须提前写死。

函数 `_extract_extra()` 的逻辑很简单：

```text
如果字段是数字：
    保存到 extra

如果字段是字典，字典里面有数字：
    保存到 extra

如果是数值数组：
    取最大值，保存到 extra

如果全程都是同一个值：
    删除，因为没有分析价值
```

所以主指标是固定字段，未知的数值指标放在 `sample.extra` 中，后面按需分析。

## 3. JSON 和 XLSX 都支持

- `parse_perfdog_json()`：解析 JSON；
- `parse_perfdog_xlsx()`：解析 Excel。

Excel 中会找：

```text
DeviceInfo
Data_v4
@FrameInfo
```

最终两者都会变成相同的 `MetricsBundle`，后面的检测逻辑不用区分数据来源。

# 三、先判断目标帧率

函数：`infer_target_fps()`

代码不会直接认定所有游戏目标都是 60 FPS。

它会：

1. 收集整段录制的 FPS；
2. 取中位数；
3. 匹配到常见档位：30、45、60、90、120、144；
4. 再看哪一档附近的 FPS 数据最多；
5. 最终确定目标帧率。

例如：

```text
大部分 FPS 在 115~125
→ 推断目标帧率为 120 FPS
→ 帧预算 = 1000 / 120 = 8.33ms
```

这个帧预算后面用来判断 FrameTime 是否严重超标。

# 四、性能异常是怎么检测的

函数：`detect_anomalies()`

这一部分**不调用 AI**，完全是本地规则。

它目前检查 5 类异常。

## 1. FrameTime 峰值

FrameTime 越高，说明单帧越慢。

判断阈值：

```text
阈值 = max(2 × 帧预算, 平均值 + 3 × 标准差)
```

例如目标 60 FPS：

```text
帧预算 = 16.67ms
2 倍帧预算 = 33.34ms

如果某帧是 150ms
→ 明显异常
```

多个距离很近的 FrameTime 峰值会合并，只保留最严重的一个，避免同一次卡顿重复报很多条。

## 2. FPS 骤降

不是 FPS 比目标低一点就报警。代码要求同时满足：

```text
FPS < 目标帧率的 60%
FPS < 平均 FPS 的 70%
FPS < 流畅线
```

比如 60 FPS 游戏：

```text
FPS = 55
→ 不算严重问题

FPS = 20
→ 可能满足三个条件，判为 FPS 骤降
```

## 3. BigJank

只要 PerfDog 某秒有：

```text
BigJank > 0
```

就直接记录，因为这是 PerfDog 已经判定出的明显大卡顿。

## 4. CPU 尖峰

App CPU 同时满足：

```text
高于 平均值 + 2.5 × 标准差
并且 > 40%
```

才算异常，避免普通波动被误报。

## 5. CPU/GPU 温度持续上升

温度不是看瞬间峰值，而是看趋势：

```text
前 20% 时间的平均温度
和
后 20% 时间的平均温度

差值 >= 8℃
→ 认为有持续升温趋势
```

# 五、为什么要把异常点合并成事件

函数：`group_anomalies_into_events()`

同一次卡顿，往往会同时出现：

```text
FrameTime 高
BigJank
FPS 降低
```

如果分别报三条，会让报告看起来像三个问题。

所以代码把：

- 同一张截图；
- 时间相差不超过 2 秒；

的异常合并成一个 `AnomalyEvent`。

最终会变成：

```text
第 120 秒，截图 120.jpg：
FrameTime 峰值 + BigJank + FPS 骤降
```

这就是后面 AI 要分析的最小单位。

---

# 六、为什么不是所有异常都发给模型

`analyze.py` 最多取 25 个事件做 AI 分析。

函数：`select_top_events()`

它不是简单选最严重的 25 个，而是尽量保证：

- 不同异常类型都覆盖；
- 不同时间段都覆盖；
- 严重问题优先。

比如录制 20 分钟，前 2 分钟连续掉帧很多次，后面又有温度问题。  
如果只按严重度排序，可能全是前 2 分钟的掉帧。这个函数会尽量把后面的温度问题也放进报告。

# 七、截图场景识别怎么做

模块：`agent/vision_agent.py`

类：`SceneAnalysisAgent`

输入：图片路径或图片字节。  
输出：结构化的 `SceneAnalysis`。

模型需要返回：

```text
app_name           应用名称
app_category       应用类型
platform           平台
scene_category     场景类别
scene_description  场景描述
key_ui_elements    关键 UI
confidence         置信度
reasoning          判断说明
```

例如：

```text
应用：某游戏
场景：战斗中打开背包
描述：角色在战斗场景内，背包面板刚打开
```

## 具体调用步骤

1. `_encode_image()`  
   把图片转成 Base64 Data URL。

2. `_build_messages()`  
   把系统提示词、任务描述、图片拼成模型输入。

3. `_call_llm_messages()`  
   调用 OpenAI 兼容接口。

4. 强制模型调用：

```text
report_scene_analysis
```

5. 从工具调用参数中读取 JSON。

6. `_normalize()`  
   清洗结果：
   - 缺失字段改成“未知”；
   - 置信度限制到 0~1；
   - UI 元素统一转成字符串列表。

## 多帧上下文

联合分析里不会只给模型一张异常图。

`analyze_with_context()` 会发送：

```text
前一帧
当前异常帧
后一帧
```

当前帧是最终判断对象，前后帧只用于理解过程。

例如：

```text
前帧：战斗画面
当前帧：黑屏
后帧：加载完成进入大厅

模型可以判断：
当前黑屏属于“战斗结束后的场景切换”
```

而不是单看黑屏就说“不明异常”。

# 八、场景识别为什么有缓存

缓存文件：

```text
compare_results.json
```

`ensure_scenes()` 的逻辑：

```text
如果截图以前识别成功过：
    直接读缓存

如果没有识别过：
    调用视觉模型

识别成功：
    写进缓存
```

因此第二次运行同一个数据集时，已经识别过的异常截图不会再次花模型费用。

缓存版本是 `2`，因为现在的场景识别带了前后帧；旧版单帧缓存会自动失效并重新识别。

# 九、场景和指标怎么联合分析

模块：`agent/joint_analyzer.py`

类：`JointAnalyzer`

这是项目最重要的“解释层”。

它不直接把所有指标塞给模型，而是分两步。

## 第一步：分诊

函数：`_call_triage()`

输入：

```text
异常事件：
- FrameTime 峰值
- BigJank
- FPS 骤降

截图场景：
- 战斗中释放技能

核心指标：
- FPS
- FrameTime
- CPU
- 温度
- Jank
- BigJank

可继续查看的维度：
- GPU
- 内存
- CPU
- 网络
```

模型输出两个字段：

```text
preliminary_judgment
suspected_dimensions
```

例如：

```text
初步判断：
战斗特效场景下帧耗升高，CPU 不高，可能偏 GPU 或资源加载问题。

需要下钻：
GPU、内存
```

## 第二步：按需读取指标

代码根据模型选择的维度，从 `extra` 中拿真实数据。

例如模型选了 GPU 和内存，代码就调用：

```text
get_dimension_metrics(bundle, ts, "GPU")
get_dimension_metrics(bundle, ts, "内存")
```

可能得到：

```text
GPU：
GPU 占用 = 98%
DrawCall = 1800

内存：
PSS = 2100MB
Java Heap = 500MB
GC 次数 = 4
```

只有模型怀疑的维度才会读取和发送，避免 Prompt 太大。

## 第三步：最终联合结论

模型最终输出：

```text
picture_state         当前画面在做什么
metrics_explanation   各指标意味着什么
joint_analysis        场景 + 指标结合后的根因判断
likely_acceptable     当前异常是否可能可接受
```

Prompt 对模型有两个硬要求：

```text
有真实数据：
必须引用具体数值

没有真实数据：
可以猜，但必须明确写“推测”
```

例如：

```text
GPU 占用 98%，CPU 仅 32%，且发生在特效密集战斗中，
说明 GPU 侧压力更明显。

如果没有 GPU 数据：
可以写“推测可能是 GPU 压力”，
但必须说“本次没有 GPU 占用或 DrawCall 数据，无法确认”。
```

# 十、聚类分析是怎么做的

模块：`agent/retest_planner.py`

类：`RetestPlanner`

联合分析完成后，可能得到很多事件：

```text
120 秒：战斗中 FrameTime 高
145 秒：战斗中 FrameTime 高
180 秒：战斗中 FrameTime 高
300 秒：加载时黑屏
```

这时项目不希望生成四份重复的复测方案，而是要把它们归为“问题模式”。

## 第一选择：让 LLM 做语义聚类

函数：`_semantic_cluster_with_retry()`

它给模型每个事件的：

- 时间；
- 场景类别；
- 场景描述；
- 异常类型；
- 联合分析结果。

模型返回：

```text
组名：战斗特效密集时的 GPU 渲染卡顿
事件：0、1、2
理由：都发生在战斗场景，现象一致，根因方向相近

组名：加载切换阶段的黑屏阻塞
事件：3
理由：与战斗卡顿属于不同流程和不同问题
```

程序会校验：

- 每个事件必须被分到某一组；
- 不允许同一事件进多个组；
- 不允许事件 ID 越界；
- 每组都要有名称和理由。

如果模型连续失败，才降级为简单规则：

```text
场景类别 + 异常类型
```

# 十一、复测方案怎么生成

一个聚类只生成一个复测方案。

例如聚类：

```text
战斗特效密集时的 GPU 渲染卡顿
```

模型会生成：

```text
问题概述
根因假设
复测步骤
观察指标
预计耗时
结果判读
```

关键点是：模型不能随便写要观察什么指标。

代码会从本次真实采集到的指标中收集列表，例如：

```text
FPS
FrameTime
BigJank
CPU(App)
GPU 占用
内存 PSS
```

如果模型写：

```text
观察 Shader 编译耗时
```

但这次没有采集 Shader 编译耗时，代码会判定输出不合格，并让模型重写。

如果模型多次调用都失败，就生成一个固定兜底方案，例如：

```text
重复进入目标场景 10 次；
记录 FPS、FrameTime；
若仅第一次出现，可能是首次资源加载；
若每次出现，可能是确定性性能问题。
```

# 十二、画面异常分析：和性能主链路分开

运行方式：

```powershell
python analyze.py --dataset dataset7 --visual-range 300-400
```

只做画面扫描：

```powershell
python analyze.py --dataset dataset7 --visual-range all --visual-only
```

模块：`agent/visual_scan.py`

目的：发现指标检测发现不了的问题，例如：

```text
白屏
花屏
模型破面
贴图缺失
大面积色块
画面错位
UI 错乱
闪烁
```

这里的关键设计是：

```text
不先做本地规则过滤。
指定时间范围内的所有截图都送模型看。
```

因为纯画面问题可能没有任何 FPS、Jank、CPU 异常。

## 每帧模型输出什么

每张截图都返回：

```text
scene        当前属于什么场景
observation  客观画面描述
persistence  出现多久、是否连续
verdict      normal / suspect / abnormal
issue_type   问题类型
evidence     给人工看的判断依据
confidence   置信度
severity     low / medium / high
```

其中：

- `normal`：正常；
- `suspect`：可疑，需要人工看；
- `abnormal`：明显异常。

## 为什么按 6 帧一批

常量：

```text
BATCH_SIZE = 6
OVERLAP = 1
```

意思是：

```text
第 1 批：1、2、3、4、5、6
第 2 批：6、7、8、9、10、11
```

第 6 帧在下一批中只作为上下文，不要求重复输出。

这样模型可以判断：

```text
白屏是只闪了一帧，
还是连续持续了 5 秒。
```

默认最多 3 批并发执行，通过环境变量控制：

```text
VISUAL_CONCURRENCY=3
```

## 为什么还要整段复核

单批最多只有 6 帧，模型可能出现：

```text
300 秒：判正常
305 秒：判异常
310 秒：判正常
```

但三帧实际画面可能很接近，判定不一致。

所以扫描结束后会调用 `cross_review()`：

1. 把所有帧的文字描述放到整段时间线上；
2. 让模型定位哪些帧判定不一致；
3. 对需要调整的帧重新写最终结论；
4. 只有新结论文字返回成功，才替换旧结果。

这样报告里最终展示的结论会更一致。

# 最后用一句话总结代码设计

这个项目的实际逻辑是：

```text
Python 先用明确规则找性能异常，
再按异常时刻找图，
让视觉模型解释画面，
让语言模型结合指标做归因，
最后把相似问题聚类，并生成复测建议。
```

如果你愿意，我下一步可以继续用这种方式，专门把以下其中一块讲透：

1. `metrics.py` 的异常检测逻辑；  
2. `visual_scan.py` 的画面异常识别逻辑；  
3. `joint_analyzer.py` 的“两阶段 AI 分析”逻辑；  
4. `retest_planner.py` 的聚类和复测方案逻辑。

明白了。你要的是“**功能说明为主，代码实现思路补一层**”，而不是函数级拆解或算法细节。

以后我会控制在这个层级：

# 1. 截图场景识别 Agent

## 功能

识别一张截图属于什么应用、什么场景、用户正在做什么。

例如识别为：

```text
某游戏
战斗中
正在打开背包
加载切换阶段
登录弹窗
```

## 怎么实现

核心模块是 `vision_agent.py`。

它把截图转成模型可读的图片输入，再调用多模态模型。模型输出不是随意的一段话，而是固定格式的场景信息，例如应用名、场景类别、场景描述、置信度。

## Prompt 的设计思路

Prompt 不是直接问“这是什么图”，而是引导模型按观察顺序判断：

```text
先看整体画风和画面比例
→ 再看文字、按钮、图标
→ 再看游戏 UI、角色、地图、弹窗
→ 最后判断当前处于什么操作或流程阶段
```

另外专门告诉模型：

```text
PerfDog 的 FPS、CPU、内存悬浮窗不是游戏画面内容，
不要因为看到这些数值而误判场景。
```

对于性能异常图，项目还会把前一帧、当前帧、后一帧一起给模型。这样模型能理解画面是“正在切换”“刚进入加载”还是“突然黑屏”。

## 为什么这样设计

单张截图只适合识别“画面是什么”；  
连续三帧更适合判断“画面正在发生什么”。

这对分析黑屏、转场、加载、打开/关闭 UI 特别重要。

# 2. PerfDog 性能异常检测

## 功能

从 PerfDog 数据里找出值得关注的性能问题，例如：

```text
卡顿帧
FPS 突降
BigJank
CPU 突然升高
设备持续升温
```

## 怎么实现

核心模块是 `metrics.py`。

这里不依赖 AI，而是先用本地规则分析指标曲线。它会读取 PerfDog 的逐秒数据和逐帧数据，识别明显偏离正常水平的时间点。

然后为每个异常点关联一张最近的截图。

## 设计思路

项目把“发现异常”和“解释异常”分开：

```text
本地规则负责发现异常
AI 负责解释异常
```

这样更可靠。

因为模型适合看图、理解业务场景、组织分析语言；  
但“FrameTime 是否明显异常”“FPS 是否大幅下降”更适合由明确规则判断。

## 为什么要把异常合并成事件

同一次卡顿可能同时表现为：

```text
FrameTime 上升
FPS 下降
BigJank 出现
```

项目会把它们合并成一个“异常事件”，而不是分成三条独立问题。

这样后面的 AI 分析会围绕一个完整现象展开：

```text
在什么画面下，
发生了一次什么样的卡顿，
可能是什么原因。
```

# 3. 场景 + 指标联合分析 Agent

## 功能

把“曲线异常”翻译成测试人员能理解的问题描述。

例如不只说：

```text
120 秒 FrameTime 180ms
```

而是说：

```text
在战斗特效集中释放时出现明显卡顿；
CPU 没有明显升高，但 GPU 侧压力较大；
更像渲染负载问题，需要进一步复测确认。
```

## 怎么实现

核心模块是 `joint_analyzer.py`。

它拿到三类信息：

```text
截图场景识别结果
异常事件中的指标变化
设备和性能数据
```

然后让模型做联合判断。

## Prompt 的设计思路

Prompt 重点约束模型三件事：

### 1. 必须结合场景

模型不能只看数值。

例如：

```text
加载时短暂黑屏
```

和：

```text
战斗操作中突然黑屏
```

虽然可能都有 FPS 为 0，但严重程度完全不同。

### 2. 有数据才能下结论

Prompt 要求模型：

```text
如果数据里有 GPU、内存、CPU 等证据，
就引用实际数值说明。

如果没有采集到相关数据，
可以提出可能性，但必须标注为推测。
```

这样避免模型把“猜测”写成“确定根因”。

### 3. 先判断方向，再补数据

联合分析不是一开始把所有指标发给模型。

它先让模型根据核心数据判断：

```text
更像 CPU 问题？
GPU 问题？
内存问题？
资源加载问题？
```

如果模型怀疑 GPU 或内存，再补充对应的详细指标。

## 为什么这样设计

这样有两个好处：

```text
减少无关数据，模型更容易抓重点；
避免每次都发送大量 GPU Counter、内存明细，节省 Token。
```

# 4. 问题聚类

## 功能

把多个相似异常收敛成少数几个“问题模式”。

例如报告中可能有：

```text
120 秒战斗卡顿
145 秒战斗卡顿
180 秒战斗卡顿
```

如果场景和原因相近，项目会把它们归纳为：

```text
战斗特效密集阶段的重复渲染卡顿
```

而不是生成三份几乎相同的结论和复测建议。

## 怎么实现

核心模块是 `retest_planner.py`。

它把每个事件的：

```text
场景
异常类型
时间
联合分析结论
```

交给模型做语义归类。

## Prompt 的设计思路

Prompt 会强调：

```text
场景相似不代表一定是一类问题；
根因相似也要结合流程阶段判断。
```

例如：

```text
启动加载黑屏
对局中的黑屏
```

不能因为都叫“黑屏”就合并。

又例如：

```text
战斗卡顿，但一个是 GPU 压力，
一个是内存 GC，
```

也应该拆成不同问题模式。

## 兜底思路

如果模型聚类失败，代码会退回更简单的规则：

```text
场景类别 + 异常类型
```

所以聚类不会因为模型一次调用失败导致整个报告无法生成。

# 5. 复测方案生成

## 功能

针对每一个问题模式，生成一份测试人员能实际执行的复测建议。

例如：

```text
重复进入某个场景；
连续触发某个操作；
观察 FrameTime、FPS、GPU；
根据是否首次出现、是否稳定复现来判断问题方向。
```

## 怎么实现

还是在 `retest_planner.py` 中完成。

它不是对每个异常事件生成方案，而是对聚类后的问题模式生成方案。

## Prompt 的设计思路

Prompt 要求方案必须具备：

```text
明确目标：要验证什么；
明确步骤：怎么操作、重复多少次；
明确指标：重点观察什么；
明确判读：不同结果说明什么。
```

同时限制模型：

```text
只能推荐本次 PerfDog 实际采集到的指标。
```

比如没有采到 GPU 占用，模型不能把“观察 GPU 占用”写成当前方案的核心观察项。

## 为什么这样设计

普通 AI 建议常常太泛，例如：

```text
建议优化性能；
建议检查内存；
建议增加监控。
```

这个项目希望输出的是测试人员可直接执行的方案，而不是泛泛建议。

# 6. 画面异常扫描 Agent

## 功能

发现“性能指标可能正常，但画面本身有问题”的情况。

例如：

```text
白屏
花屏
贴图丢失
模型破面
大面积画面遮挡
UI 错乱
渲染错位
```

## 怎么实现

核心模块是 `visual_scan.py`。

指定一个时间范围后，项目会取这个范围内的所有截图，批量发送给视觉模型分析。

它和性能异常主链路是分开的：

```text
性能异常：看指标是否异常
画面异常：看画面状态是否正常
```

## Prompt 的设计思路

这个 Prompt 最重要的原则是：

```text
不要求模型先判断“原因”，
而是先判断“这帧画面作为正常游戏画面是否成立”。
```

因为模型有时会把异常解释成：

```text
可能是技能效果；
可能是特效；
可能是转场。
```

但项目更关心的是：

```text
玩家能不能正常看清画面、正常操作。
```

所以模型会输出三种结果：

```text
normal：画面正常
suspect：有可疑现象，需要人工确认
abnormal：画面明显异常
```

## 为什么分批并带重叠帧

画面问题通常与时间有关。

例如：

```text
只闪一帧白屏
持续 5 秒白屏
消失后又重复出现
```

这些严重程度不同。

因此项目每批传入连续截图，并让相邻批次有一张重叠图，用于帮助模型判断持续性。

最后还会做一次全时间段复核，避免前后相似画面被判成不同结果。

# 7. 云端 MCP 模式

## 功能

不需要先下载 PerfDog 文件，也能直接分析线上报告。

运行方式：

```powershell
python analyze.py --caseId <报告ID>
```

## 怎么实现

核心模块：

```text
perfdog_mcp.py
cloud_source.py
```

流程是：

```text
通过 MCP 拉取报告元数据和时序指标
→ 转换成项目内部统一格式
→ 按异常时间拉取对应截图
→ 复用本地模式的整套分析逻辑
```

也就是说，云端和本地最大的差别只是“数据从哪里来”。

后面的：

```text
异常检测
场景识别
联合分析
聚类
复测方案
HTML 报告
```

都是同一套代码。

# 8. 报告与缓存

## 场景缓存

`compare_results.json` 保存截图识别结果。

这样重复分析同一数据集时：

```text
同一张截图不用重复调用视觉模型。
```

## 结果文件

主要产物是：

```text
joint_results.json
```

保存每个性能异常事件的联合分析。

```text
retest_plans.json
```

保存聚类后的复测方案。

```text
visual_issues.json
```

保存画面异常逐帧结果。

```text
joint_report.html
```

生成可直接打开的完整报告。

## 报告设计

HTML 不是只放结论，而是把证据链展示出来：

```text
异常截图
→ 场景描述
→ 指标快照
→ AI 联合分析
→ 下钻数据
→ 复测建议
```

这样测试人员看报告时能知道结论来自哪里，而不是只看到一句“可能是 GPU 问题”。
