# 多报告对比技术细节答疑整理

> 以下内容从“请你重新给我讲一下现在多报告对比的技术细节”开始，按原回答内容整理。

---

## 一、现在多报告对比的技术细节

现在的多报告对比，本质上是一条“**异步受理 → Agent 自主取数 → 结构化报告 → 程序校验和修正 → 单次回调交付**”的链路。它不是单纯把多份报告丢给模型总结，而是把模型的能力限制在“分析和归因”，把数值、报告顺序、JSON 结构、回调状态这些确定性部分交给程序处理。

---

# 1. 整体调用链

调用方通过：

```http
POST /compareAnalyze
```

提交任务，传入：

- `taskId`
- `uid`
- `compareType`
- `cases`：2~5 份报告，每份包含 `seq`、`caseId`，以及平台、机型、版本等可选元信息
- `businessContext`：例如“本次重点看版本回归”“目标 60 FPS”等业务补充

整体流程是：

```text
调用方
  ↓
Fastify /compareAnalyze
  ↓
参数校验、场景映射、创建回调 Writer
  ↓
立即返回 accepted
  ↓
后台异步执行 CompareAgent
  ↓
MCP 获取性能报告数据工具
  ↓
LangChain ReAct Agent 自主调用工具
  ↓
生成 9 模块结构化 JSON
  ↓
Zod 校验、工具事实回填、根因与建议复审
  ↓
按 seq 注入前端引用字段 ref
  ↓
HTTP 回调最终结果
```

接口层不等待模型完成，而是马上返回：

```json
{ "ret": 0, "msg": "accepted" }
```

原因是多报告分析可能跑几分钟。如果 HTTP 请求一直挂着，容易受到网关超时、调用方断开、浏览器刷新等影响。后台通过 `runWithLogger()` 异步执行，同时保留 `requestId`、`sessionId`、`uid` 等日志上下文，后续可以把入口请求、Agent 执行和最终回调串起来排查。

---

# 2. 请求校验和 7 类对比场景

`/compareAnalyze` 会做比较严格的输入校验：

- `taskId` 必须存在；
- `uid` 优先从 `X-Internal-Uid` 请求头拿，没有才用 body 里的 `uid`；
- 报告数量必须是 `2~5`；
- `caseId` 必须是正整数；
- `seq` 必须是 `1~5` 的整数；
- `cases` 必须严格按 `seq` 升序，不能重复；
- `compareType` 必须是 `1~7`；
- `businessContext` 如果只是空白字符串，会归一成 `undefined`，不塞进 prompt。

`compareType` 不是由模型猜的，而是业务方明确传入，后端映射成内部枚举：

| `compareType` | 内部类型 | 含义 |
|---:|---|---|
| 1 | `SAME_GAME_REPEAT_RUN` | 同游戏、同设备、同版本的重复测试 |
| 2 | `SAME_GAME_CROSS_VERSION` | 同游戏跨版本 |
| 3 | `SAME_GAME_CROSS_DEVICE` | 同游戏跨机型 |
| 4 | `SAME_GAME_CROSS_PLATFORM` | 同游戏跨平台 |
| 5 | `SAME_DEVICE_CROSS_GAME` | 同设备跨游戏 |
| 6 | `MIXED` | 多个维度混合变化 |
| 7 | `UNRELATED` | 没有可比公共维度 |

这样设计是因为“比较目的”本身是业务信息。两个包名相近的报告，模型可能误认为是重复测试，但业务方实际可能在看版本回归。跨版本、跨设备、跨平台的评价标准不同，所以不能完全交给模型判断。

需要注意一个边界：`labelIds` 当前会接收并写进模型输入，但还没有在本地把它转换成 MCP 查询的标签过滤条件，因此现在不能把它说成“已实现精确标签级对比”。

---

# 3. MCP 如何接入性能数据

多报告 Agent 使用：

```ts
MultiServerMCPClient
```

连接性能平台的数据服务。

它的作用是让模型能在运行时获得一批工具，例如读取报告统计、读取标签、查询掉帧上下文、做根因分析、拉指定时间段时序数据等。Agent 不需要在代码里把每个 HTTP 接口写死，而是通过：

```ts
mcp.getTools()
```

动态取得远端 MCP 暴露的工具，再交给 LangChain Agent。

鉴权逻辑是：

- 有 `uid` 时使用用户身份请求头；
- CLI 或测试路径没有 `uid`、但有 `token` 时，使用 MCP token 请求头；
- MCP 客户端会最多重连 3 次，每次间隔 1 秒；
- 无论分析成功、失败还是中途异常，`finally` 中都会关闭 MCP 连接。

工具 Schema 还会先经过 `sanitizeToolsSchema()` 清洗。原因是 MCP 返回的 JSON Schema 可能包含 `$schema`、`format`、`anyOf`、nullable union 等字段，而不同模型网关对这些字段支持不一致。特别是 Anthropic、Gemini 或某些 OpenAI 兼容网关，Schema 不兼容时模型甚至还没开始调用工具就会返回 400。

---

# 4. Agent 是如何构建的

核心是 LangChain 的：

```ts
createAgent()
```

底层采用 ReAct 模式，也就是模型会循环执行：

```text
看到任务
  ↓
判断缺什么数据
  ↓
调用工具
  ↓
读取工具结果
  ↓
继续判断是否需要下钻
  ↓
最后输出报告
```

CompareAgent 不挂 checkpointer，也没有 memory、skill、HITL 人工审批等工具。这和聊天 Agent 不同，因为它是一次性后台任务：

```text
固定输入：报告集合 + 对比类型 + 业务上下文
固定输出：一份完整 JSON 对比报告
```

任务完成后没有后续对话，不需要恢复现场，也不应该把上一份报告的记忆带到下一份报告里。

中间件大致按以下顺序装配：

```text
动态系统 Prompt
  ↓
Token 使用统计
  ↓
重复工具调用拦截
  ↓
工具失败重试
  ↓
reasoning 内容兜底
  ↓
最终 JSON 结构化校验与重试
```

---

# 5. 每个中间件具体做什么

## 5.1 系统 Prompt 中间件

`buildSystemPromptMiddleware()` 会把多报告分析的完整 SOP 注入模型的 system message，包括：

- 7 类对比场景的分析重点；
- 哪些工具适合采集基础数据；
- 哪些异常需要下钻；
- 哪些场景可以查询知识库；
- 最终 JSON 应该如何填写；
- 目标 8 分钟、最长 15 分钟等预算要求。

这里要区分：这些大部分是 **prompt 约束**，模型通常会遵守，但不是所有规则都由代码硬限制。

例如 prompt 要求阶段 A 对所有报告“同一轮并行取数”，但代码没有提前用 `Promise.all()` 把所有报告数据强制预拉好，最终仍然由模型是否并行调用工具决定。

---

## 5.2 Token 统计中间件

`createTokenUsageMiddleware()` 会在每次模型调用后，从 `usage_metadata` 中累计：

- 输入 token；
- 输出 token；
- reasoning token；
- 缓存读取 token；
- 缓存创建 token；
- 模型调用次数。

最终回调对业务方时，目前主要传递输入和输出 token，便于统计一份多报告分析的模型成本。

---

## 5.3 工具去重中间件

`toolDedupeMiddleware()` 用来处理模型反复调同一个接口的问题。

它不会直接用：

```ts
JSON.stringify(args)
```

判断参数是否相同，因为：

```ts
{ "caseId": 1, "metric": "fps" }
```

和：

```ts
{ "metric": "fps", "caseId": 1 }
```

语义完全相同，但普通 JSON 序列化结果可能不同。

所以它会做稳定序列化：对象 key 递归按字典序排序，数组保持原顺序。最终使用：

```text
toolName + stableStringify(args)
```

作为去重 key。

如果模型已经用完全相同的参数调用过一次工具，第二次不会真的请求远端 MCP，而是返回一条伪 ToolMessage，告诉模型：

- 相同结果已经在上文；
- 应该直接继续分析；
- 真要新数据就改时间窗、指标或 caseId。

这能减少无意义网络请求和 token 消耗。

---

## 5.4 工具重试中间件

`toolRetryMiddleware({ maxRetries: 3 })` 处理的是 MCP 工具本身失败，例如某个报告数据查询临时失败。

它和工具去重的顺序很重要：

```text
先去重
再工具重试
```

因为“重复调用”不是工具故障，而是模型逻辑问题，不应该触发重试。

---

## 5.5 reasoning 回填中间件

有些代理网关会把模型最终回答写进：

```text
additional_kwargs.reasoning_content
```

但 `content` 是空字符串。

如果不处理，前端会看到模型有思考过程，但最终正文为空；数据库或结构化层也可能拿不到结果。

`reasoningFallbackMiddleware()` 会在满足以下条件时回填：

- 不是工具调用轮；
- 没有 `tool_calls`；
- `content` 为空；
- reasoning 有内容。

它把 reasoning 写回 content，让下游流式输出、消息持久化、JSON 解析都能继续处理。

---

# 6. 模型如何分析多份报告

Prompt 把分析分成多个阶段。

## 阶段 A：基础数据采集

模型首先应该对每个 case 调用：

```text
perfdog_get_report_data(case_id)
perfdog_list_labels(case_id, include_statistics=true)
```

拿到：

- 报告元信息；
- 目标帧率；
- 平均 FPS；
- Low 1%；
- 帧时间；
- Jank、Stutter；
- 内存；
- CPU、GPU；
- 温度、功耗；
- 标签和场景信息。

这里的目标是先建立“每份报告的基础事实表”，而不是一开始就写结论。

---

## 阶段 B：异常识别

模型会基于基础统计发现异常，例如：

- FPS 达标率低；
- P95/P99 帧时间较高；
- BigJank 频率高；
- Stutter 比例高；
- 内存增长率持续增加；
- CPU 或 GPU 峰值高；
- 温度接近风险值；
- 某版本比基线明显变差。

这个阶段主要是“找出哪里有问题”，不是最终根因。

---

## 阶段 B′：知识库查询

知识库检索是可选步骤。它的用途不是直接告诉模型“根因是什么”，而是提供下钻方向。

例如模型发现：

```text
帧率不达标 + GPU 利用率偏低
```

知识库可能提示这种组合常见于主线程等待、资源加载或渲染提交阻塞，模型可以据此决定阶段 C 要进一步看 CPU、IO、内存还是网络相关指标。

知识库使用有明确限制：

- 所有报告整体达标时跳过；
- 异常都在启动前 3 秒时跳过；
- 重复测试、混合、完全不相关场景跳过；
- 跨版本、跨设备通常只查询最严重的一份；
- 跨平台、跨游戏可以按报告分别查询；
- 返回内容必须检查平台、指标锚点和现象方向是否匹配。

知识库只是辅助材料，最终根因仍应该来自当前报告的工具数据。

---

## 阶段 C：异常下钻

发现异常后，模型可以调用：

```text
perfdog_analyze_root_cause
perfdog_get_drop_context
perfdog_get_time_range_detail
perfdog_get_time_series
```

其中：

- `perfdog_analyze_root_cause` 更适合 FPS 或帧时间明显下降时使用；
- `perfdog_get_drop_context` 更适合 BigJank、Stutter 等下降事件；
- `perfdog_get_time_range_detail` 用于看指定时间区间的更细数据；
- `perfdog_get_time_series` 用于看整体趋势。

`perfdog_analyze_root_cause` 返回的数据通常已经包含：

- 掉帧区间；
- `in_drop` 帧级数据；
- 关联指标；
- 相关系数；
- 根因候选；
- 按分数排序的候选结果。

所以 prompt 会提醒模型，不要已经拿到这些数据后又机械地重复拉一遍时序。

---

## 阶段 D：最终 JSON

异常点完成归因后，模型进入最终输出阶段，填充 9 个模块：

1. 总体结论；
2. FPS；
3. 流畅度；
4. 内存；
5. CPU/GPU；
6. 温度和功耗；
7. 异常清单；
8. 根因；
9. 优化建议。

Prompt 要求模型在最终阶段不要再反复调用工具，除非某份报告从未下钻，或者某个已经识别的异常还没有归因。

---

# 7. 9 模块 JSON 的结构

最终报告由：

```ts
compareReportSchema
```

定义，使用 Zod 进行运行时校验。

顶层包含：

```text
generatedAt
title
summaryConclusion
correlation
reports
module1 ~ module9
```

其中 `reports` 保存每份报告的身份信息：

```text
reportId
seq
label
platform
deviceModel
version
targetFps
targetFpsSource
targetFpsRationale
```

这里有个关键点：模型写出的 `seq` 不完全可信。最终由：

```ts
enrichWithSeqAndRef()
```

根据请求输入的 `cases` 做一次覆盖。

它还会为模块中的对象补：

```text
ref: "r1"
ref: "r2"
```

方便前端把同一份报告在不同模块里的数据放到同一列。

---

# 8. 为什么需要 Zod 和结构化输出重试

模型最终不一定直接返回合法 JSON，可能出现：

- 输出 Markdown 说明文字；
- JSON 外包了一层解释；
- 少字段；
- 字段类型不对；
- 根因模块应该是对象却输出成数组；
- 优化建议模块层级不对；
- 没调任何工具直接编报告。

所以非 Anthropic 模型会经过：

```ts
structuredOutputRetryMiddleware
```

处理。

流程是：

```text
最终 AIMessage
  ↓
先从 content 提取 JSON
  ↓
提取不到时从 reasoning 提取 JSON
  ↓
修复常见的对象/数组结构错误
  ↓
Zod safeParse 校验
  ↓
成功后做数据回填和结论复审
  ↓
把最终对象挂回 AIMessage
```

中间件会识别三类失败：

| 类型 | 含义 | 处理 |
|---|---|---|
| `no_data_collected` | 模型没调用性能工具就写报告 | 提示回到阶段 A 采集数据 |
| `schema_failed` | JSON 能解析，但字段不符合 Zod | 返回具体字段错误，让模型定向修正 |
| `no_json` | content 和 reasoning 都没有有效 JSON | 要求基于已有数据输出纯 JSON |

最多会重试 2 次。

有两类机械错误可以直接修：

```text
module8_rootCause = []
→ module8_rootCause = { hypotheses: [] }

module9_optimization = []
→ module9_optimization = { items: [] }
```

这类问题不需要消耗一次模型重试。

# 9. 事实回填：为什么模型的数字不直接使用

这是多报告链路最重要的部分之一。

模型最终 JSON 中可能会写：

```text
r1 平均 FPS = 55
r2 平均 FPS = 60
```

但模型很可能：

- 写错报告；
- 写错统计口径；
- 算错达标率；
- 把一个没有工具来源的数字补出来；
- 把 Android 的 PSS 和 Windows 的 Working Set 混在一起。

所以 `finalizeCompareReport()` 会回放 Agent 的全部 `ToolMessage`，从工具返回里重新建立一份：

```ts
CompareToolContext
```

这个上下文包括：

```text
reportDataByCase
dropContextByCase
dropContextRule
```

其中：

- `reportDataByCase`：按 caseId 存储报告的 metadata、statistics、statisticsExtra、trends；
- `dropContextByCase`：按 caseId 存储掉帧事件、关联指标和相关系数；
- `dropContextRule`：记录本次实际使用的掉帧阈值和持续时间。

然后程序回填模块 2~6 的关键数值。

---

# 10. 哪些数值会被程序回填

## FPS 模块

程序从工具统计中读取：

```text
fps.avg
one_percent_low.avg
frame_time.p95
frame_time.p99
frame_time.var
```

分别回填：

```text
avgFps
low1pct
p95FrameTimeMs
p99FrameTimeMs
frameTimeVariance
```

达标率由程序计算：

```text
achieveRatePct = avgFps / targetFps * 100
```

---

## 流畅度模块

程序读取：

```text
small_jank.per_10min
big_jank.per_10min
stutter.avg
fps.drop_per_hour
freezeCount
```

如果工具没有直接给总 Jank，会尝试：

```text
totalJank = smallJank + bigJank
```

---

## 内存模块

程序从对应平台的内存指标中获取：

```text
avgMB
peakMB
growthRateMBPerMin
deltaMB
```

其中：

```text
deltaMB = endValue - startValue
```

趋势斜率来自工具的 trend 数据，而不是模型推测。

---

## CPU/GPU 模块

程序回填：

```text
cpuAvgPct
cpuPeakPct
gpuAvgPct
gpuPeakPct
```

但具体取哪个指标取决于平台。

---

## 温度与功耗模块

程序会尝试找温度、功耗对应的工具字段，回填平均值和峰值。

但：

```text
throttleDetected
batteryDrainPctPerHour
```

当前没有统一可靠的工具字段，因此会被强制设置为：

```text
null
```

不会根据温度高、CPU 高就猜测“发生了降频”。

---

# 11. 跨平台指标口径怎么处理

程序通过：

```ts
resolvePlatformMetricSet()
```

按平台选择不同指标候选集。

| 平台 | 内存 | CPU | GPU |
|---|---|---|---|
| Android | `memory_pss` | `cpu_total` | `gpu_usage` |
| iOS | `memory_xcode` | `cpu_total` | `gpu_device` |
| Windows | `memory_working_set` | `cpu_app` / `cpu_system` | `gpu0_sys_3D(0)` |
| macOS | `memory_working_set` | `cpu_total` | `gpu_render` |

程序不是看见某个字段名像 CPU 或内存就直接用，而是先识别平台，再在该平台候选集合里找工具真实返回的字段。

对于没有统一可比口径的字段，宁可为 `null`，或者在报告里写明口径限制，也不强行给出跨平台结论。

---

# 12. 派生指标和异常项如何校验

## Low 0.1%

程序会检查：

```text
0 < Low0.1% ≤ Low1% ≤ AvgFPS
```

不满足时直接置为 `null`。

原因是 Low 0.1% 比 Low 1% 高、或者比平均 FPS 高，通常说明指标来源或模型输出存在问题。

---

## 内存占用率

程序从 metadata 中拿设备总内存，并检查：

```text
totalDeviceMB > 0
totalDeviceMB >= peakMB
```

通过后计算：

```text
occupancyPct = peakMB / totalDeviceMB * 100
```

如果设备总内存不可信，就不计算占用率。

---

## 异常规则和异常列表

如果模型调用过：

```text
perfdog_get_drop_context
```

程序会拿实际调用时的：

```text
drop_threshold_percent
min_drop_duration_ms
```

写入异常规则，避免报告写的是默认 15%/1000ms，但模型实际查询用的是别的阈值。

异常项重建规则是：

```text
有 drop context 证据 → 用 dropEvents 重建
没有 drop context 证据 → 保留模型原异常
```

有证据时，事件按：

1. 跌幅从大到小；
2. 持续时间从长到短；
3. 起始时间从早到晚；

排序。每份报告最多保留 3 个异常项，全局最多 10 个。

早期有一个典型 bug：程序从空数组开始重建，最后无条件覆盖模型异常项；如果模型走的是根因分析工具而没有返回 drop context，就会把原异常全部清空。现在修成“有证据才覆盖”。

# 13. 为什么数据校正后还要复审根因和优化建议

数值回填会把模型初稿中的数字改成工具事实，但模块 8 的根因和模块 9 的优化建议可能是基于旧数字写的。

例如模型原来认为：

```text
平均 FPS 75，明显不达标，建议优先降低 GPU 压力
```

回填后真实平均 FPS 是：

```text
88，已经达标
```

这时根因和优化建议可能不再成立。

所以代码会构建一份“高影响事实字典”，包括：

- 可比性等级；
- best/worst/watch 报告；
- 目标帧率；
- FPS、Jank、内存、CPU/GPU、温度等核心数值；
- 各模块评级；
- 异常规则和异常项。

然后比较校正前和校正后的字典。

如果没有差异，直接保留原根因和建议。

如果变化不大，调用辅助模型做一个轻量判断：

```text
KEEP
REVISE
```

它只回答：当前 module8/module9 的结论方向是否仍然成立。

如果变化很多，或者轻量模型认为需要修改，才调用主模型定向重写模块 8 和模块 9。重写时不能修改模块 1~7，只能基于校正后的事实修改根因和优化建议。

高影响变化超过：

```text
24 项
```

时会跳过轻量判断，直接进入完整修订。

# 15. 回调如何避免重复成功或重复失败

`CompareCallbackWriter` 内部维护：

```text
settled
```

状态。

流程是：

```text
onResult()
  ↓
只缓存最终 JSON

onComplete()
  ↓
发送一次 done 回调
  ↓
settled = true

onError()
  ↓
发送一次 failed 回调
  ↓
settled = true
```

一旦 `settled=true`，后续无论收到完成还是错误事件都忽略。

成功回调通常包含：

```text
taskId
status = done
title
summaryConclusion
fullContent
inputTokens
outputTokens
```

失败回调包含：

```text
taskId
status = failed
errorMsg
```

错误信息、标题和摘要都会做长度截断，避免异常文本或模型输出过长导致回调体失控。

## 二、MCP 如何接入性能数据：进一步解释

可以。这一块其实包含四层：**MCP 客户端怎么连、工具怎么动态加载、鉴权怎么透传、工具 Schema 为什么还要清洗**。

## 1. `MultiServerMCPClient` 是什么

`MultiServerMCPClient` 是 LangChain 提供的 MCP 客户端适配器。它的作用不是直接帮模型“分析性能数据”，而是把远端 MCP 服务提供的能力转换成 LangChain 能识别的工具。

远端服务可以提供类似这些能力：

```text
读取报告统计数据
读取标签及标签内统计
查询掉帧时间区间
查询异常区间内 CPU、GPU、内存等关联指标
对 FPS 下降进行根因候选排序
读取时序曲线
查询专家知识库
```

在传统 HTTP 接入方式里，通常需要自己做三件事：

```text
1. 给每个接口写请求代码
2. 给每个接口定义参数 Schema
3. 把接口说明拼进 Prompt，要求模型按约定调用
```

这里改成 MCP 后，数据平台把工具名称、参数定义、描述和调用方式统一暴露出来。Agent 连接 MCP 服务后，能动态发现当前可调用的工具，不需要在多报告 Agent 里把每一个数据接口写死。

对应逻辑在 `CompareAgent.createMCPClient()`：

```text
588:613:perfdog-agent/src/agent/common/compare-agent.ts
public static createMCPClient(options?: { uid?: string; token?: string }): MultiServerMCPClient {
    const config = getConfig();
    const mcpUrl = config.internal?.mcp;
    if (!mcpUrl) {
        throw new Error('未配置 internal.mcp 地址，请检查配置文件或环境变量 PERFDOG_INTERNAL_MCP_URL');
    }

    const headers: Record<string, string> = {};
    if (options?.uid) {
        headers['X-PerfDog-Uid'] = options.uid;
    } else if (options?.token) {
        headers['Mcp_token'] = options.token;
    }

    return new MultiServerMCPClient({
        'perfdog-mcp-tools': {
            url: mcpUrl,
            headers,
            reconnect: {
                enabled: true,
                maxAttempts: 3,
                delayMs: 1000,
            },
        },
    });
}
```

## 2. 客户端建立连接时具体做了什么

这段代码先从配置中读取 MCP 地址：

```ts
const mcpUrl = config.internal?.mcp;
```

如果没有配置地址，直接抛异常。因为多报告分析依赖远端数据工具，MCP 地址不存在时，Agent 即使能调用模型，也无法拿到性能数据。

然后构造请求头：

```ts
const headers: Record<string, string> = {};
```

这里分两种身份模式。

### 用户身份模式：`uid`

正常业务请求会传用户 ID。客户端添加：

```http
X-PerfDog-Uid: <uid>
```

远端数据平台根据这个用户身份判断他能访问哪些报告、项目和数据。

### Token 模式：`token`

CLI、本地测试或某些非业务入口不一定有 uid，这时使用：

```http
Mcp_token: <token>
```

这种方式通常用于 MCP Key 鉴权。

这里的优先级是：

```text
有 uid → 用 uid
没有 uid、但有 token → 用 token
```

之所以不用两个都传，是因为代码希望明确当前请求采用哪一种身份语义，避免远端服务对权限来源产生歧义。

## 3. 为什么配置了重连 3 次、间隔 1 秒

MCP 是远端连接，可能因为网络抖动、服务短暂重启、连接被中间网关关闭而失败。

所以客户端配置为：

```ts
reconnect: {
  enabled: true,
  maxAttempts: 3,
  delayMs: 1000,
}
```

它解决的是“**连接建立或连接维持阶段**”的问题：

```text
第一次连不上
  ↓
等 1 秒
  ↓
再次尝试
  ↓
最多尝试 3 次
```

这里要区分它和后面 Agent 流执行时的重试：

- `MultiServerMCPClient.reconnect`：解决 MCP 客户端的连接问题；
- `toolRetryMiddleware({ maxRetries: 3 })`：解决某一次工具调用失败；
- `streamOnce()` 的上游重试：解决模型网关空响应、5xx、超时或连接重置。

它们对应不同故障位置，不能笼统说“系统有三次重试”。

## 4. `mcp.getTools()` 到底返回了什么

MCP 客户端建立后，`buildAgent()` 会执行：

```ts
const mcpTools = await mcp?.getTools();
```

它会向 MCP 服务拉取所有工具定义，并转换成 LangChain 的 `StructuredTool[]`。

每个工具可以理解为包含以下信息：

```text
工具名
工具用途说明
参数 Schema
真正执行调用的方法
```

例如一个“获取报告统计”的工具，模型看到的不是 HTTP URL，而是类似：

```text
工具名：perfdog_get_report_data
用途：读取指定 caseId 的性能统计、元信息和趋势数据
参数：case_id
```

Agent 在运行中把这些工具作为可选动作交给模型。模型根据当前任务决定调用哪个工具：

```text
先读所有报告基础统计
  ↓
发现 r2 FPS 明显下降
  ↓
调用掉帧上下文或根因分析工具
  ↓
读取关联指标和相关系数
  ↓
形成根因和优化建议
```

对应代码如下：

```text
645:664:perfdog-agent/src/agent/common/compare-agent.ts
let tools: StructuredTool[] = [];
try {
    const mcpTools = await mcp?.getTools();
    if (mcpTools) {
        tools.push(...mcpTools);
    }
} catch (err) {
    logger.warn({err}, '获取 MCP 工具失败，agent 将无可用工具');
}

sanitizeToolsSchema(tools);
```

这里有一个实际边界：如果 `getTools()` 失败，代码只是记录 warn，然后创建一个**没有任何工具的 Agent**。这不等于任务必然成功；后面结构化输出层会发现没有工具数据，要求模型重新采集，但如果 MCP 一直不可用，最终会失败或进入降级路径。

## 5. 为什么工具不是写死在代码里

动态获取工具的好处主要有三点。

### 5.1 数据平台可以独立演进

数据团队以后新增：

```text
GPU 细分指标查询
网络抖动分析
磁盘 IO 查询
新的根因分析工具
```

只要 MCP 服务把它暴露出来，Agent 下次启动获取工具时就能发现。CompareAgent 不必为每个新接口重新发布。

### 5.2 模型能看到参数定义

工具参数不是只靠 prompt 文字说明，而是通过 Schema 描述。例如模型知道某工具需要：

```json
{
  "case_id": 123,
  "target_metric": "fps",
  "drop_threshold_percent": 15,
  "min_drop_duration_ms": 1000
}
```

这样模型调用工具时，LangChain 能帮助约束参数结构。

### 5.3 多报告 Agent 与数据服务解耦

CompareAgent 负责分析编排：

```text
什么时候该拉数据
什么时候该下钻
如何生成报告
如何校验和回填
```

MCP 服务负责数据能力：

```text
如何访问报告
如何计算掉帧区间
如何输出相关系数
如何查询知识库
```

这两个部分可以独立迭代。

## 6. 为什么 `getTools()` 后还要执行 `sanitizeToolsSchema()`

这是多模型兼容里比较容易踩坑的一点。

MCP 返回的工具会带 JSON Schema，用来描述参数结构。标准 Schema 可能长这样：

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "case_id": {
      "type": "integer",
      "minimum": 1,
      "format": "int64"
    },
    "platform": {
      "anyOf": [
        { "type": "string" },
        { "type": "null" }
      ]
    }
  }
}
```

这从 JSON Schema 标准角度没有问题，但不同模型接口支持的只是其中一部分。

常见兼容问题包括：

| 字段 | 为什么可能出问题 |
|---|---|
| `$schema` | 某些模型网关不接受 Schema 版本声明 |
| `format` | 例如 `int64`、`date-time`，部分网关不识别 |
| `minimum`、`maximum` | 有些工具调用接口不支持数值范围约束 |
| `minItems`、`maxItems` | 某些模型服务不支持数组范围限制 |
| `anyOf` | nullable 字段常用 `anyOf: [string, null]` 表示，部分接口对 union 类型数量有限制 |
| `additionalProperties` | 有些 OpenAI 兼容后端会拒绝或错误处理 |

例如：

```json
{
  "anyOf": [
    { "type": "string" },
    { "type": "null" }
  ]
}
```

会被清理或折叠成更兼容的形式：

```json
{
  "type": ["string", "null"]
}
```

目的不是修改业务参数含义，而是让 Schema 以各模型网关更容易接受的格式传出去。

## 7. Anthropic、Gemini、OpenAI 兼容网关为什么都要特殊处理

不同模型的工具调用链不完全一样。

### Anthropic 路径

Claude 对 JSON Schema 和工具参数有自己的限制，特别是复杂 `anyOf`、多层 union、`$schema` 等字段可能导致网关拒绝，所以 CompareAgent 在获取 MCP 工具后会统一清洗。

### OpenAI 兼容路径

Gemini、部分内部模型或者代理网关表面上走 OpenAI 协议，但实际后端可能更严格。

项目里的 `LLMFactory` 针对 `ChatOpenAI` 做了两层处理：

```text
第一层：调用 bindTools() 前，清洗每个 tool.schema
第二层：LangChain 把工具转换成 OpenAI function 定义后，再清洗 function.parameters
```

之所以做两层，是因为有时工具 Schema 是 Zod 对象，有时已经是普通 JSON Schema；有时入口修改没生效，出口还可以兜底。

对应实现说明：

```text
147:170:perfdog-agent/src/agent/llm/factory.ts
对 ChatOpenAI 兼容口模型做 schema 清洗补丁……
通过 OpenAI 兼容网关转发到 Google Gemini 后端时，
Gemini 对 OpenAPI 子集要求严格，不接受 `$schema`、`format`、
`additionalProperties`、数值上下界等 JSON Schema 关键字……
```

实际问题不是“模型不会分析”，而是工具参数 Schema 在请求发出前就被网关拒绝。这个兼容层保证 Agent 至少能进入工具调用阶段。

## 8. MCP 工具如何真正进入 Agent

模型和工具最后在这里合并：


`tools` 就是从 MCP 动态拿到、并经过 Schema 清洗的工具数组。

当模型需要数据时，会输出一个工具调用请求。LangChain 会：

## 9. 为什么最终还要关闭 MCP 连接

`compare()` 的结构大致是：

```ts
const mcp = CompareAgent.createMCPClient({ uid, token });

try {
  // 创建 Agent、运行分析、处理结果
} catch (error) {
  // 记录错误、回调失败
} finally {
  await mcp.close().catch(() => {});
}
```

这里把关闭放在 `finally` 中，保证以下场景都能释放资源：

```text
模型调用失败
工具调用失败
JSON 校验失败
数值回填异常
模块 8/9 复审异常
回调链路异常
```

否则多报告任务并发执行时，长期未关闭的 MCP 长连接可能逐渐占满连接池、文件句柄或网络资源。

## 10. 这部分在面试时怎么讲

可以这样表达：

> 多报告 Agent 通过 `MultiServerMCPClient` 接入性能数据平台。MCP 的作用是把远端的报告统计、掉帧上下文、根因分析等能力动态转换成 LangChain 工具，Agent 启动时通过 `mcp.getTools()` 获取工具列表，因此数据平台新增工具时不需要在 Agent 中逐个写死 HTTP 接口。  
>
> 接入过程中我重点处理了两件事：一是按用户 ID 或 MCP Token 透传身份信息，保证远端按权限返回报告数据；二是做工具 Schema 兼容。MCP 返回的是标准 JSON Schema，但 Claude、Gemini 和部分 OpenAI 兼容网关对 `$schema`、`anyOf`、`format` 等字段支持不一致，如果不清洗，模型可能还没调用工具就直接 400。  
>
> 工具接入后，模型按 ReAct 流程决定先取哪些报告数据、哪些异常需要下钻。所有工具结果会保存在 LangChain 的 ToolMessage 中，后续报告生成完成后，程序还会从这些 ToolMessage 回放原始统计数据，校正模型写入的 FPS、Jank、内存、CPU/GPU 等数值。

## 三、为什么 `getTools()` 后还要执行 `sanitizeToolsSchema()`：简单解释

`sanitizeToolsSchema()` 可以理解成：**给模型看的“工具使用说明书”做一次格式整理**。

`mcp.getTools()` 拿到的并不只是工具名，还会拿到每个工具的说明和参数定义。例如“查询报告数据”这个工具，会带一份 Schema，告诉模型：

```json
{
  "工具名": "get_report_data",
  "参数": {
    "case_id": "整数，必填",
    "start_sec": "数字，可选",
    "end_sec": "数字，可选"
  }
}
```

模型需要先看懂这份参数说明，才能生成正确的工具调用。

问题在于，这份说明书采用的是标准 JSON Schema 格式，里面可能有很多细节字段，例如：

```json
{
  "$schema": "https://json-schema.org/...",
  "type": "object",
  "properties": {
    "case_id": {
      "type": "integer",
      "minimum": 1,
      "format": "int64"
    },
    "platform": {
      "anyOf": [
        { "type": "string" },
        { "type": "null" }
      ]
    }
  }
}
```

这些字段本身没有业务问题，但不同模型服务对“工具参数说明”的支持程度不同。

比如：

- 有的模型服务能理解 `anyOf`，即“这个字段可以是字符串，也可以是 null”；
- 有的模型服务不接受 `anyOf` 这种复杂写法；
- 有的服务不认识 `$schema`、`format: int64`；
- 有的服务只接受最简单的 `type + properties + required` 格式。

如果原样把这份 Schema 发给模型网关，可能还没开始分析报告，就报：

```text
400 Bad Request：工具参数格式不支持
```

所以在：

```ts
const mcpTools = await mcp.getTools();
sanitizeToolsSchema(mcpTools);
```

这里，`sanitizeToolsSchema()` 做的事情就是把“功能不变、但格式复杂”的参数说明，转换成“功能不变、但大多数模型都能接受”的简单写法。

例如：

```json
{
  "anyOf": [
    { "type": "string" },
    { "type": "null" }
  ]
}
```

可能会整理为：

```json
{
  "type": ["string", "null"]
}
```

又例如：

```json
{
  "type": "integer",
  "minimum": 1,
  "format": "int64"
}
```

会保留模型真正需要知道的：

```json
{
  "type": "integer"
}
```

`minimum: 1` 和 `format: int64` 这类限制会被移除，因为它们对模型“知道该传整数”帮助不大，却可能导致某些网关拒绝整份 Schema。

所以这一层不修改工具本身：

```text
不会改工具名
不会改工具参数值
不会改 MCP 服务逻辑
不会改报告数据
```

它只修改**发给模型的工具参数说明格式**，让同一批 MCP 工具可以更稳定地被 Claude、Gemini、OpenAI 兼容模型等不同模型服务识别。

---

## 四、`sanitizeToolsSchema()` 是我们定义的一个工具吗？用的大模型还是函数？

`sanitizeToolsSchema()` **不是大模型，也不是 MCP 工具**，而是项目里自己写的一个普通 TypeScript 函数。

它的输入是：

```ts
tools: StructuredTool[]
```

也就是 `mcp.getTools()` 返回的工具列表。

它的输出不是新工具，而是直接修改这批工具的 `schema` 字段，把参数说明整理成模型网关更容易接受的格式。

调用关系是：

```text
MCP 服务
  ↓
mcp.getTools()
  ↓
拿到一批工具及各自的参数 Schema
  ↓
sanitizeToolsSchema(tools)
  ↓
清理 Schema 中不兼容的字段
  ↓
createAgent({ model, tools })
  ↓
大模型看到整理后的工具说明并调用工具
```

所以：

- `mcp.getTools()`：远端 MCP 服务返回工具；
- `sanitizeToolsSchema()`：本地普通函数，整理工具的参数说明；
- `createAgent()`：把模型和整理后的工具组合成 Agent；
- 大模型：在 Agent 运行时，根据工具说明决定是否调用工具。

它的定义位置在：

```text
src/agent/schema/anthropic.ts
```

名字里虽然有 `anthropic`，但并不代表它只能给 Claude 用。当前多报告 Agent 对所有 MCP 工具都会执行一次这个清洗函数，因为 OpenAI 兼容模型、Gemini 或代理网关也可能受益。

---

## 五、Zod 进行运行时校验，Zod 是什么？它是如何保证 JSON 格式统一的？它是怎么用的？

`Zod` 是一个 TypeScript / JavaScript 的**运行时数据校验库**。

TypeScript 本身只能在开发阶段检查类型。例如代码里写：

```ts
type Report = {
  title: string;
  avgFps: number;
};
```

编译时会提醒开发者类型问题，但模型返回的数据、HTTP 请求体、MCP 工具结果都是运行时才出现的。模型可能返回：

```json
{
  "title": 123,
  "avgFps": "60"
}
```

这段 JSON 语法是合法的，但数据类型不符合要求。TypeScript 在运行时不会拦它，Zod 就是用来拦这种情况的。

---

## 它如何统一 JSON 格式

先用 Zod 写一份“报告应该长什么样”的 Schema。例如简化后的写法：

```ts
const reportSchema = z.object({
  title: z.string(),
  avgFps: z.number().nullable(),
  rating: z.enum(["GOOD", "FAIR", "POOR", "N/A"]),
  hypotheses: z.array(
    z.object({
      cause: z.string(),
      confidence: z.number(),
    }),
  ),
});
```

这份 Schema 表达的是：

```text
title 必须是字符串
avgFps 必须是数字，也允许为空 null
rating 只能是四种固定值之一
hypotheses 必须是数组，数组每项都必须有 cause 和 confidence
```

多报告项目里的 `compareReportSchema` 更大，它定义了：

```text
顶层标题、摘要、报告元信息
模块 1：总体结论
模块 2：FPS
模块 3：流畅度
模块 4：内存
模块 5：CPU/GPU
模块 6：温度和功耗
模块 7：异常项
模块 8：根因假设
模块 9：优化建议
```

因此它统一的不是“JSON 缩进、换行或是否用 Markdown 包裹”，而是**JSON 解析后的对象结构**：字段名、字段类型、字段是否允许为空、数组层级、枚举取值范围。

---

## 在这个项目中它怎么用

整个过程可以理解为：

```text
模型输出文本
  ↓
先尝试提取 JSON
  ↓
JSON.parse 后得到 JavaScript 对象
  ↓
用 compareReportSchema 检查对象
  ↓
通过：进入数值回填、根因复审、回调
失败：根据错误内容让模型定向重试
```

项目中不是直接调用会抛异常的：

```ts
compareReportSchema.parse(data)
```

而是主要使用：

```ts
const result = compareReportSchema.safeParse(data);
```

`safeParse()` 的特点是不会直接抛错，而是返回两种结果。

### 校验成功

```ts
{
  success: true,
  data: {
    // 已确认结构符合 Schema 的报告对象
  }
}
```

后续代码可以放心读取：

```ts
result.data.module2_fps.perReport
result.data.module8_rootCause.hypotheses
```

因为这些字段已经经过类型和层级校验。

### 校验失败

```ts
{
  success: false,
  error: {
    issues: [
      {
        path: ["module2_fps", "perReport", 1, "avgFps"],
        message: "Expected number, received string"
      }
    ]
  }
}
```

这里的 `path` 非常重要。它能精确指出模型哪里错了：

```text
第 2 个报告的 FPS 模块中，avgFps 应该是数字，
但模型返回了字符串。
```

项目会把这类错误整理成定向提示，告诉模型：

```text
你上次 JSON 可以解析，但字段结构不符合要求。
请修正 module2_fps.perReport[1].avgFps，
只输出完整 JSON，不要额外解释。
```

模型最多重试两次。

---

## Zod 不能做什么

Zod 不是模型，也不会自动让模型“更聪明”。它不能保证模型第一次就输出正确 JSON，也不会自动判断“FPS 60 合不合理”。

它能保证的是：

```text
只有符合规定结构的数据，才能被当作正常报告继续处理。
```

例如：

| 问题 | Zod 能否发现 |
|---|---|
| `avgFps` 写成 `"60"` 字符串 | 可以 |
| 根因模块少了 `hypotheses` | 可以 |
| 优化建议写成对象而不是数组 | 可以 |
| `rating` 写成不支持的 `"VERY_GOOD"` | 可以 |
| JSON 少一个右括号，无法解析 | 不能直接处理，需先由 JSON 解析层发现 |
| FPS 数值是 999，但类型是 number | Schema 默认发现不了，需要额外业务规则或工具数据回填 |
| 模型把 r1 的 FPS 写到 r2 | 类型校验发现不了，需要后面的 MCP 原始数据回填 |

所以当前项目是几层配合：

```text
JSON 提取层
  解决：模型有没有输出可解析 JSON

Zod Schema
  解决：字段名、字段类型、数组层级、枚举值是否统一

工具事实回填
  解决：模型写的 FPS/Jank/内存等数字是否真实

模块 8/9 复审
  解决：数值被修正后，根因和优化建议是否还成立
```

Zod 在这里承担的是“**结构统一和接口契约校验**”这一层。

---

## 六、Zod 和 Pydantic 做校验有什么区别？

作用基本一样：**都用于在运行时校验数据结构**。

区别主要是语言生态不同：

| 对比项 | Zod | Pydantic |
|---|---|---|
| 常用语言 | TypeScript / JavaScript | Python |
| 常见用途 | 前端、Node.js、TypeScript 后端 | Python 后端、FastAPI、数据处理 |
| 定义方式 | `z.object()`、`z.string()`、`z.number()` | Python 类 + 类型注解 |
| 校验方式 | `safeParse()` / `parse()` | `model_validate()` / 创建 Model |
| 校验失败 | 返回 `{ success: false, error }` 或抛异常 | 抛出 `ValidationError` |
| 类型推导 | 可从 Schema 自动推导 TypeScript 类型 | 可从 Python 类型注解生成校验模型 |

Zod 示例：

```ts
const ReportSchema = z.object({
  title: z.string(),
  avgFps: z.number().nullable(),
});

const result = ReportSchema.safeParse(data);
```

Pydantic 示例：

```py
class Report(BaseModel):
    title: str
    avg_fps: float | None = None

report = Report.model_validate(data)
```

在这个多报告项目里，后端是 TypeScript，所以用 Zod；如果同样的项目是 Python/FastAPI 后端，通常就会用 Pydantic。

它们在这里承担的职责是一样的：**确保模型输出的 JSON 符合后端和前端约定的数据结构。**

## 七、数值回填步骤
1. Agent 调 MCP 工具获取多份报告数据
   ↓
2. LLM 基于工具结果，先生成一份完整的 9 模块 JSON 报告
   ↓
3. Zod 校验 JSON 结构
   - 字段类型、数组层级、必填字段不对 → 定向重试
   ↓
4. 程序回放 MCP 工具原始结果
   - 按 caseId 回填 FPS、Jank、内存、CPU/GPU、温度等核心数值
   - 本地重算达标率、内存占用率等派生指标
   - 有掉帧上下文时，重建异常清单
   ↓
5. 对比“模型初稿”与“数据回填后的报告”的高影响事实
   ↓
6. 判断模块 8 根因、模块 9 优化建议是否还成立
   - 没有数值变化 → 原样保留
   - 有小范围变化 → 用辅助模型判断 KEEP 或 REVISE
   - 变化很多，或辅助模型认为结论受影响 → 调主模型重写模块 8、模块 9
   ↓
7. 注入 seq/ref 等前端展示字段
   ↓
8. 回调最终报告
